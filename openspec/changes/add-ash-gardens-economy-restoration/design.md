# Design — Ash Gardens, Economy & Restoration Domains (P6)

## Context

Ownership rows 5–11 of `docs/architecture/elixir/ownership.md` are the last gameplay domains whose authority Node holds, and the only ones where incorrect concurrency can destroy or duplicate player wealth. Today's implementation shape:

- **State**: `data/game-state.json` — `players` (map of guestId → `{id, nickname, coins, xp, level, reputation, reservedCoins, inventory: {seeds, produce, reservedProduce, sprinklers}, materials, currentRoom, lastSeen}`), `gardens` (playerId → `{beds[12], fixtures?}`), `orders`, `trades` (kept 100), `marketMultipliers` (per item float), `nodes` (nodeId → depletedAt ms), `machines` (`{mill: {status, required {copper 4, timber 4, glass 4}, contributed, restoredAt}}`). One synchronous whole-file rewrite on nearly every mutation (`server/storage.js`).
- **Gardens** (`server/gardens.js` + `shared/gardenModel.js`): 12 beds, 4×3 grid. `tickBed(bed, dtSeconds=1, isRaining, now, sprinkled)` runs at 1 Hz for gardens loaded in memory: moisture ±floats (`+0.05·dt` when raining/sprinkled, else `−dt·(0.008·waterDemand | 0.005)`), health (`−0.002·dt` when moisture ≤ 0.05, floor 0.2; else `+0.001·dt`, cap 1.0), `moistureHistorySum += moisture·dt`, `moistureChecks += dt` (a float), and `stage = getGrowthStage(plantedAt, duration, now)` — pure timestamp math (thresholds 0.15/0.45/0.75/1.0 of `growDuration` or `regrowDuration` for repeat-harvest crops). There is **no offline catch-up for moisture/health/history**: a garden not in the in-memory map simply doesn't tick; when reloaded it resumes from persisted floats with `lastTick = Date.now()`. Stage self-corrects because it is a function of `plantedAt` vs `now`. Weather (`isRaining`) is the 3-minute world rotation; only `RAIN` waters (`server/index.js:1172`).
- **Actions**: `garden_action` (owner-only check `gardenOwner !== playerId`), with inventory mutations done *by the handler after* `gardens.handleAction` succeeds — plant: seeds−1, xp+3 (no level recompute); harvest: produce+yield, xp+crop.xp, **level recomputed** `floor(xp/100)+1`; place_sprinkler: kits−1. Reason strings: `bed_not_found`, `invalid_bed`, `occupied`, `not_prepared`, `already_planted`, `unknown_crop`, `not_ready`, `fixture_already_present`, `sprinkler_limit_reached`.
- **Economy** (`server/economy.js` + `shared/economy.js`): NPC sell price `max(1, Math.round(base·mult·qualMult·0.85))`, seed price `max(1, Math.round(seedCost·(1+(mult−1)·0.4)))`; multiplier update `m += netDemand·0.03` then `m += (1−m)·0.05`, clamp [0.4, 2.5], `Number(m.toFixed(3))`; netDemand `+0.2·qty` (seed buy) / `−0.5·qty` (sell; goods forced grade B). Sell grants xp `Math.round(qty·3)` with **no level recompute**.
- **Order book** (`server/orderbook.js` + `server/index.js:714-790`): client-supplied `orderId` trusted; price/qty `Math.round`ed; escrow moves coins→`reservedCoins` (buy, `totalCost = Math.round(price·quantity)`) or produce→`reservedProduce` (sell) *before* matching; matching is price-time with **maker-price execution**, a **crop-mismatch break** (`if (bestAsk.cropId !== cropId) break` — breaks the whole loop, it does not skip ahead), **self-match allowed** (no `playerId` check); fee `max(1, Math.round(value·0.02))` deducted from seller proceeds; on fill, the buyer's reservation is debited by `trade.price · trade.quantity` — the **maker (execution) price, not the taker's limit price** — leaving price-improvement residue stuck in `reservedCoins` (see D5); cancel refunds `remaining · price`. Trade ids are random and pinned out of parity fixtures.
- **Contracts** (`server/economy.js:131-269`): 3-slot board, memory-only, regenerated at boot; reroll every 5 min (`tickContracts`); each contract gets `expiresAt = now + 10 min` (display data — completion never checks it); flour contracts only while the mill is restored; completion walks `Object.entries(produce)` — **JS insertion order is semantic** (which grades get consumed first) — quality rank C<B<A<A+ vs `minQuality`, `insufficient_qualifying_produce` when short, rewards `round(base·1.35-or-1.0·qty·1.4)`, rep `round(qty·5)`, xp `round(qty·8)`, level recomputed.
- **Nodes/machines** (`server/nodes.js`, `server/machines.js`): 9 nodes across foundry/trestle/frost-spire, 180 000 ms respawn, depletion timestamps persisted (restart-safe by design); harvest has a check-then-set race (two players, one node). Mill contribution: `applied = min(floor(requested), held, remaining)`, `material_fulfilled`/`insufficient_materials`/`invalid_quantity`/`mill_already_restored`/`material_not_needed` guards, restoration completes in the step that receives the final unit; mill consumes wheat `C→B→A→A+` → `flour_B` 1:1; sprinkler craft costs `{copper: 2, glass: 2}`, max 3 per garden, coverage = bed + orthogonal neighbors in the 4-column grid (`sprinklerCoverage`).
- **Level math**: `level = floor(xp/100)+1`, recomputed only on harvest and contract completion (not on plant/npc_sell xp).
- Parity hazards that bind this change: `js_round = floor(x + 0.5)` (half toward +∞), `toFixed(3)` binary-float formatting must not be approximated, floats (moisture/health/multipliers) must stay floats, JSON integral floats render without a decimal point, key-order-semantics sites (contract deduction order, MILL_REQUIREMENT/SPRINKLER.cost order, CROP_LIST order), and error reason strings are wire protocol.

See proposal.md for motivation; the three capability specs for behavior contracts.

## Goals / Non-Goals

**Goals:**
- One authority-group flip for rows 5–11: after cutover, PostgreSQL is the only writer for gardens, wallets, inventory, market, orders, trades, contracts, nodes and machines.
- Money and inventory correctness enforced by the database: integer columns, nonnegative CHECKs, conditional reservation debits (`WHERE reserved >= delta`), one transaction per fill with a deterministic lock ladder, idempotent retries, at-least-once outbox.
- Bit-faithful port of the deterministic rules: growth, quality, prices, multiplier chains, matching (incl. crop-mismatch break and self-match), fee, level math, contribution clamp, grade-consumption order — gated by the P0 fixtures.
- Byte-compatible client payloads and exact error reason strings; zero client changes.
- Auditable conservation: every balance change writes a ledger row; import validates totals and conservation before the flip.
- Deterministic, benchmarked contention behavior for market fills (p95 ack < 250 ms same-region target).

**Non-Goals:**
- No deterministic offline moisture/health catch-up (documented follow-up — see D6).
- No new gameplay: no order-book improvements (price-improvement refund, crop-skip matching), no contract expiry enforcement, no new beds/crops/nodes/machines, no auction fees change.
- No accounts/identity redesign (P4 owns sessions and signed identity; this change merely activates the P4 shadow `players` rows as writer with the group flip) and consumes signed identity and receipts.
- No movement/presence work (P3 owns it); no theater/catalog changes (P5); no load/soak harness (P10 owns fleet-wide load; this change ships only the fill-contention benchmark).
- No client-side changes, including `marketModal.js` (price parity makes previewing correct by construction).

## Decisions

### D1 — The group flips as one atomic authority unit
*Decision:* Router flips gardens + economy + restoration message domains in a single cutover commit; Node's corresponding write paths are disabled in the same release. During implementation the Elixir domains run behind the parity/integration suites with routing still on Node; the flip is one configuration change in the gateway domain map (`Afterlight.Gateway.Router`), exercised first in a staging environment.
*Alternative Considered:* Flipping per-domain (gardens first, market later). Rejected: a `harvest` on Phoenix crediting jsonb inventory on Node (or an order fill on Node mutating a garden-grown `produce` balance on Phoenix) splits one player's money across two writers with no transaction boundary spanning them — exactly the dual-write state `migration-governance` forbids. The domains are mutually referential (harvest→inventory→orders→contracts→mill→gardens via flour), so only the whole group is a safe unit.

### D2 — Full data model: normalized tables with database-enforced money rules
*Decision:* Migrations create (all quantities/coins `bigint`, all ms timestamps `bigint` epoch ms to match wire values, floats as `float8`):

- `gardens` — `player_id` PK/unique FK→players, timestamps. `beds` — id, `garden_id` FK, `index` (0–11), `prepared` boolean, `crop_id` text null, `planted_at` bigint null, `last_watered_at` bigint null, `moisture` float8 default 0, `health` float8 default 1.0, `moisture_history_sum` float8 default 0, `moisture_checks` float8 default 0 (float — `+= dtSeconds`), `stage` int (0–6), `harvest_count` int default 0; CHECK `index BETWEEN 0 AND 11`; unique `(garden_id, index)`. `sprinklers` — id, `garden_id`, `bed_index`, `type` default `'sprinkler'`; unique `(garden_id, bed_index)` (enforces `fixture_already_present` under concurrency); per-garden count ≤ 3 enforced in the placing transaction (`sprinkler_limit_reached`).
- `wallets` — `player_id` PK/unique, `coins` bigint not null default 0, `reserved_coins` bigint not null default 0; CHECK `coins >= 0`, `reserved_coins >= 0`. **No `reserved_coins <= coins` CHECK — it is not an invariant** (two overlapping escrows can make reserved exceed spendable coins; see D5).
- `inventory_balances` — `player_id`, `item_kind` (`'seed' | 'produce' | 'reserved_produce' | 'material' | 'fixture'`), `item_id` text (`cropId`, `cropId_quality` e.g. `flour_B`, material id, or `sprinklers`), `quantity` bigint not null, `acquired_seq` bigint not null (see D7); CHECK `quantity >= 0`; PK `(player_id, item_kind, item_id)`; index `(player_id)` for `inventory_state` builds. Zero-quantity rows are **deleted**, mirroring JS `delete obj[key]` semantics (key presence in payloads + acquisition-order behavior).
- `market_multipliers` — `item_id` PK, `multiplier` float8 not null (exact double; see D4), `updated_at`.
- `orders` — `id` text PK (the client `orderId`, which is the envelope `request_id`), `player_id`, `side` check in (`'buy','sell'`), `crop_id`, `quality`, `price` bigint CHECK `price > 0`, `quantity` bigint CHECK `quantity > 0`, `filled` bigint not null default 0 CHECK `filled BETWEEN 0 AND quantity`, `created_at` bigint (price-time tiebreak), `cancelled_at` bigint null, `inserted_at`. Fully-filled and cancelled orders stay as rows (audit + trade references). Indexes: `orders_matching_bids` on `(crop_id, price DESC, created_at, id)` `WHERE side='buy' AND cancelled_at IS NULL AND filled < quantity`; symmetric `orders_matching_asks` `(crop_id, price ASC, created_at, id)` `WHERE side='sell' AND …`.
- `trades` — bigserial PK, `public_id` text unique (wire `trade.id`, generated server-side, masked in fixtures), `buyer_id`, `seller_id`, `crop_id`, `quality`, `price` bigint, `quantity` bigint, `value` bigint, `fee` bigint CHECK `fee >= 1`, `executed_at` bigint, `taker_order_id`/`maker_order_id` FKs.
- `ledger_entries` — bigserial PK, `player_id`, `kind` (`'npc_buy' | 'npc_sell' | 'order_escrow_coins' | 'order_escrow_produce' | 'order_fill' | 'order_cancel_refund' | 'fee' | 'harvest' | 'plant' | 'contract_reward' | 'node_gather' | 'mill_contribute' | 'mill_output' | 'craft' | 'import'`), `account` (`'coins' | 'reserved_coins' | 'produce' | 'reserved_produce' | 'seed' | 'material' | 'fixture' | 'xp' | 'reputation'`), `item_id` null, `delta` bigint (signed), `trade_id` null FK, `command_ref` null (receipt), `inserted_at`. Every durable balance/xp/reputation mutation writes one row in the same transaction; the table is the audit trail for conservation checks.
- `contracts` — `id` text PK (wire id `contract_<ts>_<slot>`), `slot` int CHECK `BETWEEN 0 AND 2` unique (one live board), `client`, `crop_id`, `crop_name`, `quantity` bigint, `min_quality`, `reward` bigint, `reputation` bigint, `xp` bigint, `tier` null, `expires_at` bigint, `generated_at` bigint. Board meta (`last_refresh_at`) in a one-row `contract_board` table so the 5-min cadence survives restart.
- `gather_nodes` — `node_id` PK, `district`, `material`, `depleted_at` bigint null, `respawn_ms` bigint not null default 180000.
- `machines` — `machine_id` PK (`'mill'`), `status` check in (`'broken','restored'`), `restored_at` bigint null. `machine_materials` — PK `(machine_id, material)`, `required` bigint, `contributed` bigint, CHECKs `required >= 0`, `contributed >= 0`, `contributed <= required`. `machine_contributions` — bigserial PK, `machine_id`, `player_id`, `material`, `applied` bigint CHECK `applied > 0`, `inserted_at` (audit).
- `command_receipts` / `outbox_events` — as established in P4 (`(actor_id, request_id)` PK with `payload_hash` + stored response jsonb; outbox with unique `event_id`, monotone `revision`, `published_at`).

*Activation and the P4 shadow columns (review fix):* the P4 `players` row carries money/xp columns (`coins`, `reserved_coins`, `xp`, `level`, `reputation`, CHECKed) as a read-only shadow. At this change's activation, those columns are DROPPED (or, if any reader still needs them, transactionally mirrored from `wallets` in every balance write — dropped is the default) so money never has two writable representations; the `inventory_state`/player wire payload is built from `wallets`/`inventory_balances` only, never from `players` money columns; and the cutover validation report SHALL include a players↔wallets agreement check proving the shadow columns and the activated balances agreed at freeze time.

*Alternative Considered:* Keeping players' money inside a `players` jsonb column with application-level checks — rejected: it reproduces today's bug surface (no constraint fires, no transaction isolates, no audit); `runtime.md` §PostgreSQL model and the governance spec both require explicit integer balances with constraints. Storing orders as an ordered jsonb array to mimic book order — rejected: SQL indexes express price-time order natively and lock rows individually.

### D3 — The market fill: one SQL transaction, per-market advisory lock, fixed lock ladder
*Decision:* `Afterlight.Economy.MarketFill.execute/2` is the only writer of fills. It opens one transaction and, per fill inside the matching loop, performs — in this order: (1) maker order `filled += q` via conditional update, (2) escrow release + credit for buyer (`reserved_coins` conditional debit, `produce` credit), (3) seller credit (`coins += value − fee`) + `reserved_produce` conditional debit, (4) trade row, (5) ledger rows for every delta incl. the `fee` row, (6) after the loop: taker order remainder insert-or-update, command receipt response, outbox events — all `COMMIT`ed or rolled back together. The conditional order update comes FIRST within each fill (review correction): 0 rows affected means the maker's remaining quantity shrank under us, and the WHOLE transaction is aborted and the fill retried against the re-read book — abort-and-retry, never continue-against-a-stale-remainder. Because the remainder update precedes every escrow-debit/produce-credit step for that fill, an aborted fill has moved no money and no items. `cancel_order` SHALL acquire the same per-crop advisory lock before refunding, so a cancel can never interleave between a fill's order-remainder update and its balance movements (the remaining-vs-escrow race is closed by lock order, not by hope). Bounded raw Ecto/SQL is explicitly permitted here per `port-backend-to-elixir` design (ADR-008 layering): Ash changes compose the *response*, the transaction itself is hand-written SQL because it must be.

**Lock ladder** (every transaction in the group acquires in this order, never out of order — the ladder covers EVERY table the group writes):
1. `pg_advisory_xact_lock(hashtextextended('market:' || crop_id, 0))` — matching transactions only;
2. `market_multipliers` rows, `item_id` ascending (npc trades only);
3. `players` rows, `player_id` ascending (xp/level writes during harvest and contract completion);
4. `wallets` rows, `player_id` ascending (`SELECT … FOR UPDATE`);
5. `inventory_balances` rows, `(player_id, item_kind, item_id)` ascending;
6. `beds` rows, `(garden_id, index)` ascending;
7. `orders` rows, `id` ascending (`FOR UPDATE`, locked in matching visit order after the advisory lock makes it safe);
8. `contracts` rows, `slot` ascending;
9. `machines` rows, `machine_id` ascending (the D11 lock point that also serializes `machine_materials`).

Produce-first flows (contract completion deducting produce before crediting coins) SHALL acquire in ladder order — wallets before inventory where both are touched — so no flow can deadlock against a market fill for the same player.

**Why a per-market advisory lock instead of ordering player ids:** the set of wallets a fill touches is not known until matching completes — the maker list depends on which resting orders cross, and price-time iteration can revisit a maker after a partial fill. Sorted-by-player-id locking requires the set up front and still needs the book itself serialized; a transactional advisory lock keyed by crop market gives deadlock-free, single-writer matching per market with one line, keeps different crops fully concurrent, and composes with the ladder for npc trades (which skip step 1). Contention is bounded by one market's trade rate; the benchmark task (tasks §7) measures fill latency under 2 buyers × 1 resting order and a mixed 8-crop load, with an explicit p95 < 250 ms same-region ack target and a documented fallback (split the advisory key to `(crop_id, price_bucket)` only if measurements demand it).

Oversell and negative balances are database-enforced regardless of lock discipline: `UPDATE orders SET filled = filled + $q WHERE id = $id AND quantity - filled >= $q` (0 rows affected → abort the whole transaction with retry per the D3 fill ordering — the remainder update runs before any balance movement, so the retry starts from clean state), `UPDATE wallets SET reserved_coins = reserved_coins - $q WHERE player_id = $p AND reserved_coins >= $q`, and CHECK constraints as the backstop. The ledger property (verified per transaction in tests): for each trade, Δ(buyer coins) + Δ(buyer reserved) + Δ(seller coins) = `−fee`, and item flows mirror escrow flows exactly.
*Alternative Considered:* Pure row-lock ordering by player id (rejected above); a single global advisory lock for all markets (simplest, needlessly serializes unrelated crops — keep as the emergency fallback if the benchmark shows hot markets starving others); serializing fills through one GenServer per market (violates "GenServer state alone SHALL NOT be relied upon for financial correctness" and adds a failover hazard).

### D4 — Numeric parity: js_round, float8 multipliers, JSON number rendering
*Decision:* One `Afterlight.Parity.Numeric` module: `js_round(x)` = `floor(x + 0.5)` (half toward +∞, fixture-pinned incl. negatives), used at every JS `Math.round` site (prices, order price/qty normalization, fees, contract rewards, xp); `js_to_fixed_3(x)` reproducing `Number(x.toFixed(3))` (the binary-float formatting quirk — never `Float.round`, which is half-even); `js_max/js_min` where JS coercions matter. Multipliers are stored as `float8` — the exact IEEE double survives PG round-trip, so `read → math → js_to_fixed_3 → store` chains identically to JS. All timestamps are epoch-ms integers; garden dt is the float `1.0`. Elixir JSON encoding for wire payloads renders integral floats without a decimal point (JS `JSON.stringify(1.0) === "1"`) and uses shortest-round-trip float formatting, verified by a payload-parity test suite (D9).
*Alternative Considered:* `Decimal`/`Numeric` columns for money — rejected for the *multipliers* (would break `toFixed(3)` bit parity by design; prices derived from them must match JS to the coin) and unnecessary for coins (already integers). `trunc(round(x))` — rejected: half-away-from-zero ≠ JS for negatives; fixture-table pins the difference.

### D5 — Escrow parity, including the price-improvement residue quirk
*Decision:* Port escrow arithmetic exactly as observed in `server/index.js:714-817`: buy escrow at `Math.round(price·quantity)`; on fill, buyer's `reserved_coins` debited by `exec_price · q` (maker price) and seller paid `value − fee` — therefore **price-improvement residue stays in the buyer's `reserved_coins`** and coins+reserved conservation still holds globally (Δ(coins)+Δ(reserved) = −fee per trade; the residue is an accounting sink inside reserved, not a leak). Cancel refunds `remaining · price`. No `reserved_coins <= coins` constraint exists (overlapping escrows can legitimately make reserved exceed spendable coins); instead the DB enforces `reserved >= 0` and every reservation debit is a conditional update. This quirk is **documented, fixture-pinned, and deliberately not "fixed"** — refunding residue would change `inventory_state` payloads (player-visible) and belongs in a post-migration economy change with its own proposal.
*Alternative Considered:* Debiting reservations at the limit price on fill (what most exchanges do) — cleaner accounting but diverges from the wire-visible `reservedCoins` field today; rejected under parity-before-authority.

### D6 — Garden tick: faithful 1 Hz port now; deterministic offline catch-up is a follow-up
*Decision:* `Afterlight.Gardens.Tick` is one 1 Hz scheduler (no per-bed process, per `runtime.md`) that ticks all *loaded* gardens with `dtSeconds = 1.0` and `is_raining` from the `Afterlight.World` weather runtime (only `:rain` counts; drizzle does not water). Loaded semantics are FAITHFUL-FIRST, and the behavior being mirrored is stated precisely (review correction — an earlier draft claimed beds pause while nobody is in the garden room): today, Node's hello handler calls `getOrCreateGarden` for EVERY connecting player and `GardensManager.tick` iterates that map forever with no eviction — i.e. gardens tick for every player who has connected since boot, regardless of room occupancy. The Elixir policy mirrors exactly that: loaded = a live session exists for the garden's owner; a garden is loaded at hello; there is no eviction (a disconnected player's garden keeps ticking until restart, as in Node). Bed math ports `tickBed` line-for-line in the same float accumulation order (`moisture → health → moistureHistorySum += moisture·dt → moistureChecks += dt → stage from plantedAt`), so fixture sequences (incl. multi-step scripts) reproduce exactly. On load, a garden resumes from persisted floats and its `stage` self-corrects via timestamp math — **exactly today's semantics: no moisture/health/history catch-up for offline or unloaded gardens** (a player who has not connected since boot has no garden in memory and does not tick). Deterministic catch-up (applying elapsed time analytically on load) is a separate follow-up change because it is not parity-portable: `moistureHistorySum`/`moistureChecks` accumulate per-second floats whose values depend on the *sequence* of 1 Hz steps and on weather history the server never recorded, so an analytic shortcut cannot reproduce harvest quality. Any lazy-loading alternative (e.g. ticking only gardens whose owners occupy their garden room) is likewise a DECLARED follow-up requiring its own behavior-change justification — it would change which beds grow and which quality histories accumulate — never a silent optimization inside this migration. This change documents both gaps and leaves a `Gardens.Tick` seam where the catch-up policy would slot in.
*Alternative Considered:* Compute growth purely from timestamps and derive moisture analytically (decay is linear until dry) — rejected for this phase: quality depends on the accumulated history, not just current moisture, so "equivalent" analytic state changes harvest grades (user-visible). Also rejected: one process per bed (process count and wakeups scale with beds, contradicting `runtime.md`'s explicit guidance).

### D7 — Inventory normalization from the frozen snapshot jsonb + acquisition-sequence ordering
*Decision:* Player inventory reaches this change as Node-authored JSON in the frozen `game-state.json` snapshot (the P4 accounts change carries the same shape as an interim jsonb schema plus shadow import, but — with P4 narrowed to session authority — the shadow is a migration-source rehearsal, NOT this import's source). This change imports it into `inventory_balances` rows keyed by `(player_id, item_kind, item_id)` with nonnegative quantities: `seeds` → kind `seed`, `produce` (`cropId_quality`) → `produce`, `reservedProduce` → `reserved_produce`, `materials` → `material`, `inventory.sprinklers` → `fixture/sprinklers`. Rows that reach zero are deleted; rows re-created after deletion get a fresh monotonically-increasing `acquired_seq`. This reproduces the one place where JS object insertion order is semantic in this group: **contract produce deduction** walks `Object.entries(produce)` — acquisition order, with deleted-at-zero keys re-appended on re-acquisition. `complete_contract` selects eligible grades ordered by `acquired_seq`, yielding the identical deduction sequence. NPC sell / mill / placement follow the same delete-at-zero rule so payload key presence matches JS exactly (no zero-valued keys in `inventory_state`).
*Alternative Considered:* Ordering deduction by quality rank (B before A, etc.) — deterministic but *not* what the JS does (insertion order can consume A+ before B if the player bought A+ first), changing which grades remain after a contract; rejected. Preserving jsonb insertion order in a `jsonb` column — `jsonb` normalizes keys, and per-player money still needs relational constraints; rejected.

### D8 — Idempotency receipts + outbox for every durable command
*Decision:* All fourteen Ash actions (`till_bed`, `water_bed`, `plant_bed`, `harvest_bed`, `place_sprinkler`, `npc_buy`, `npc_sell`, `place_order`, `cancel_order`, `complete_contract`, `gather`, `contribute_to_machine`, `mill_wheat`, `craft_sprinkler`) run inside the receipt protocol: first statement of the command transaction inserts `(actor_id, request_id, payload_hash)` with `ON CONFLICT DO NOTHING`; a conflict with the same hash returns the stored response verbatim (exactly-once effect under client retry/reconnect), a conflict with a different hash is rejected as a protocol error. The garden `actionId`, order `orderId`, and node/machine `actionId` all map to the envelope `request_id` (garden/node actionIds were already client-generated correlation ids — now they get exactly-once teeth). Receipt-key coverage per the governance requirement: command classes WITHOUT a client correlation id — `market_buy`, `market_sell`, `contract_complete` (and `set_nickname`, which routes at this change's players activation) — get SERVER-MINTED receipt ids with documented NO-DEDUP interim semantics (transport-level at-least-once delivery; effects are idempotent-by-value where defined, e.g. price/quantity-derived market ops), stated here explicitly. Broadcasts (`garden_state`, `market_update`, `contract_update`, `node_state`, `machine_update`, `inventory_state`, `trade_filled`) are written as `outbox_events` in the same transaction and published at-least-once by the outbox dispatcher; consumers (gateway sessions) dedupe by `(event_id, revision)` — a redelivered fill event cannot double-credit any client view, and replay after reconnect is safe.
*Alternative Considered:* Publishing via PubSub straight from the action (today's shape) — loses the crash window between commit and broadcast, and `migration-governance` requires the outbox; receipts only for market commands — rejected, harvest/node/machine rewards are exactly the "retry cannot duplicate rewards" case the spec calls out.

### D9 — Wire parity: payload builders pinned per message
*Decision:* A single `Afterlight.Protocol.Payloads` module builds every migrated S→C message with documented field order mirroring the JS object-literal insertion order: `garden_state {roomId, beds[index,prepared,cropId,plantedAt,lastWateredAt,moisture,health,moistureHistorySum,moistureChecks,stage,harvestCount], fixtures?}`, `inventory_state {player[id,nickname,coins,xp,level,reputation,reservedCoins,inventory{seeds,produce,reservedProduce,sprinklers},materials,currentRoom,lastSeen]}` (zero-value inventory keys absent, `sprinklers` key present only when > 0), `market_update {prices, orderBook{bids,asks,trades≤20}}` with price entries `{cropId,name,basePrice,multiplier,instantBid,instantAskSeed,seedCost}` (crops in `CROP_LIST` order, then goods with `isGood: true`), `contract_update {contracts}`, `node_state {roomId, nodes[{nodeId,material,available,depletedAt,respawnAt}]}`, `machine_update {machines{mill{status,required,contributed,restoredAt}}}`, `action_result {actionId?,success,title?,message}` with the exact JS strings (e.g. `` `Harvested ${yield}x Grade ${quality} ${name}!` ``, `'Action complete'`, `'Pried loose 1x Copper Scrap.'`), `trade_filled {trade}`, `error {message}`. Error reason strings are exactly: `insufficient_coins`, `insufficient_produce`, `invalid_order_params`, `not_found`, `node_depleted`, `mill_already_restored`, `material_not_needed`, `invalid_quantity`, `material_fulfilled`, `insufficient_materials`, `contract_not_found`, `fixture_already_present`, `sprinkler_limit_reached` — plus the legacy strings the JS already emits (`bed_not_found`, `invalid_bed`, `occupied`, `not_prepared`, `already_planted`, `unknown_crop`, `not_ready`, `mill_broken`, `no_wheat`, `unknown_fixture`, `insufficient_qualifying_produce`, `invalid_request`, `unknown_node`). A fixture suite serializes each payload from both implementations and compares keys, values, key order and number rendering. Book snapshots order bids `(price DESC, created_at ASC)` and asks `(price ASC, created_at ASC)` — the stable `sortBooks` comparators — and `trades` are the 20 most recent (latest first). The JS caps its persisted trade list at 100 on save, but the wire never exposes more than 20, so PG keeps all trade rows for audit and the snapshot query simply selects the latest 20 — observable behavior identical, retention strictly better.
*Alternative Considered:* Reusing Node's payload objects verbatim through the proxy — only available pre-flip; post-flip the builders are the contract, so they get their own fixtures.

### D10 — Node harvest race: conditional update, first writer wins
*Decision:* `gather` = one transaction: conditional `UPDATE gather_nodes SET depleted_at = $now WHERE node_id = $id AND (depleted_at IS NULL OR $now >= depleted_at + respawn_ms)` — 1 row → grant `material +1` (inventory conditional insert/update + ledger + receipt + outbox) and commit; 0 rows → `node_depleted` with `respawnAt` computed from the row just read, no side effects. District membership (`node.district === session.current_room`) is checked before the transaction, as today. The 1 Hz respawn reaper deletes elapsed `depleted_at` and emits district `node_state` events through the outbox, matching `NodesManager.tick/1` broadcast behavior.
*Alternative Considered:* `SELECT … FOR UPDATE` then check-then-set — equivalent correctness but holds the row lock across the inventory writes for no benefit; the conditional update is one round-trip and self-documents the race.

### D11 — Machine contributions: clamp parity, restore-in-same-step, audited
*Decision:* `contribute_to_machine` is one transaction over `machine_materials` (locked via `machine_id` row lock on `machines`), computing `applied = min(floor(requested), held, remaining)` with the guard ladder and reason strings preserved (`mill_already_restored` → `material_not_needed` → `invalid_quantity` → `material_fulfilled` → `insufficient_materials`); writes the player `material` debit, `contributed += applied`, an audit row in `machine_contributions`, and — when the last requirement is met in this same step — flips `machines.status = 'restored'`, stamps `restored_at`, and enqueues the mill-restoration `machine_update` + contract-board reroll `contract_update` outbox events (mirroring `server/index.js:1080-1087`). `mill_wheat` consumes `wheat_C → B → A → A+` (ordered list, never map order) 1:1 into `flour_B`; `craft_sprinkler` checks then deducts `{copper: 2, glass: 2}` in `MILL_REQUIREMENT`/`SPRINKLER.cost` key order and increments the `fixture/sprinklers` balance — all in one transaction each. Contribution is open to every authenticated actor (policy: no ownership scope); the audit table answers "who put in what" which the file never could.
*Alternative Considered:* Clamping via DB trigger — the clamp involves the player's held balance, so it belongs in the transaction; CHECKs still backstop `contributed <= required`.

### D12 — Policies: actor-scoped money, communal restoration
*Decision:* Ash policies derive the actor from the server-verified session only (P4 identity; client-supplied `playerId`/`guestId` fields are correlation data, never authorization): wallets/inventory/beds — read/write only for the owning actor (garden actions additionally assert `room_owner == actor`, preserving 'You can only cultivate your own garden.'); order placement acts on the actor's own wallet/inventory; `cancel_order` is scoped to orders `player_id == actor` (`not_found` otherwise, exactly today's response for foreign orders); `complete_contract`/`npc_*` operate on the actor's own balances; `gather` grants to the actor; `contribute_to_machine` is open to all authenticated actors (the mill is communal). Price/amount sanity: the server computes every derived amount (`totalCost`, escrow, fee, prices); client-supplied `price`/`quantity` are validated as positive integers within sane magnitude bounds (finite, ≤ 10^9 per unit, `price·quantity` ≤ 10^12 so bigint math cannot overflow) using the existing `invalid_order_params` rejection — a stricter guard than JS (which would coerce garbage into NaN) that only rejects inputs the old server would have mangled or crashed on.
*Alternative Considered:* Trusting room membership for garden ownership (anyone in `garden:<id>` may act) — matches neither today's owner check nor actor-scoping; rejected.

### D13 — Import ceremony, validation, and rollback posture
*Decision:* Cutover per `migration-governance`: (1) write freeze — Node gates the ten command types with a retryable busy response and stops its 1 Hz garden/node/contract tickers' persistence; (2) snapshot `data/game-state.json` + SHA-256 recorded in an `import_snapshots` row — with P4 narrowed to session authority, `players` (wallets and inventory jsonb included) are still Node-authored JSON at this cutover, so ALL economy-group domains (players, gardens, orders, trades, marketMultipliers, nodes, machines) import from this single frozen snapshot (the P4 shadow import was a migration-source rehearsal, not this import's source); (3) `mix afterlight.import_economy_group` runs the idempotent importer: wallets/inventory from `players` (incl. `reservedCoins`/`reservedProduce` → reservation balances), `gardens` → beds/sprinklers, `orders`/`trades` → tables (order ids kept verbatim), `marketMultipliers` → `market_multipliers` (float8 bit-exact), `nodes` → `gather_nodes`, `machines` → mill rows; every imported balance gets an `import` ledger row so the audit trail starts clean. Legacy orphaned `reservedProduce` — reserved produce exceeding the sum of the player's open sell orders — is written off at import: the importer zeroes the orphaned amount and records a documented reconciliation entry (an `import`-kind ledger note stating the written-off amount per player), so `reserved_produce = Σ open sell escrow` holds after import; (4) validation — per-player: jsonb→balance-rows equality (the file's inventory/reservation objects rebuild to exactly the imported balance rows) and file coins/reserved/inventory sums == table sums; orders-escrow ↔ reserved-pools equality across the book; `level` copied as-is (it legitimately lags xp when npc_sell was the last xp source — do **not** recompute); conservation: Σ(coins+reserved) == file total; `reserved_coins ≥ Σ remaining·price` over the player's open buy orders (≥, not =: the D5 residue makes reserved legitimately exceed open escrow — equality is required for `reserved_produce` vs open sell orders after the orphan write-off); Σ node depletions match; mill totals match; (5) a second import of the same hash is a documented no-op (idempotency keyed on snapshot hash + natural keys). **Rollback:** forward-fix preferred; after PG is authoritative, reverting to the JSON writer is not a valid rollback. The reverse export tool (writes a `game-state.json`-shaped file from PG under a fresh write freeze) exists for forensic comparison and emergency downgrade to pre-P6 builds only, accepting that actions taken post-flip are exported as best-effort state, not a lossless rewind.

*Activation and the P4 shadow columns (review fix):* the P4 `players` row carries money/xp columns (`coins`, `reserved_coins`, `xp`, `level`, `reputation`, CHECKed) as a read-only shadow. At this change's activation, those columns are DROPPED (or, if any reader still needs them, transactionally mirrored from `wallets` in every balance write — dropped is the default) so money never has two writable representations; the `inventory_state`/player wire payload is built from `wallets`/`inventory_balances` only, never from `players` money columns; and the cutover validation report SHALL include a players↔wallets agreement check proving the shadow columns and the activated balances agreed at freeze time.
*Alternative Considered:* Dual writes for a safety window — forbidden by `ownership.md` rule 4; keeping Node as hot standby via reverse export each minute — a second writer by another name; rejected.

## Risks / Trade-offs

- [Advisory-lock matching becomes a hot-spot on one crop] → per-crop keys keep unrelated markets parallel; the contention benchmark (tasks §7) must show p95 < 250 ms before flip; documented fallback is price-bucket key splitting, and the ladder keeps correctness independent of the measured number.
- [Float parity drift (moisture chains, multiplier formatting)] → all math funneled through `Afterlight.Parity.Numeric`; fixture suites run multi-step scripts (parity notes #1/#2); float8 storage round-trips bits exactly; payload tests compare serialized numbers.
- [Key-order semantics (contract deduction, payload field order, grade lists)] → `acquired_seq` reproduces acquisition order (D7); payload builders pin insertion order (D9); grade lists are ordered literals; a byte-level payload fixture suite gates the flip.
- [Faithful port bakes in known quirks (residue in reserved_coins, no offline moisture catch-up, contract expiry unenforced, self-match, crop-mismatch break)] → deliberate: each is documented in D5/D6/D11/parity fixtures with the fix path named as separate post-migration proposals; fixing them inside the migration would confound parity failures with intended behavior changes.
- [Import validates a live file that can drift between freeze and import] → the freeze stops Node writes before snapshot; the importer re-hashes at read time and aborts on hash mismatch; validation failures abort the flip (no partial authority).
- [Contract reroll randomness] → `generateContracts` uses injected RNG (parity notes #13); the live system seeds it from the entropy pool, fixtures pin it; flour-contract slot selection (`i === floor(random·3)`) ports exactly.
- [Outbox lag shows stale market state after a fill] → dispatcher is same-node, immediate, with retry/backoff; clients also resnapshot on reconnect; dedupe by `(event_id, revision)` makes redelivery harmless; outbox age is a metric from day one.
- [bigint/JS number boundary on payloads] → all migrated quantities fit far below 2^53; sanity bounds (D12) keep client-supplied magnitudes inside the safe integer range.

## Migration Plan

1. **Land behind flags (routing untouched)**: migrations + domains + parity runner green + DB integration/property suites + benchmark report. Node remains the writer; no player-visible change.
2. **Rehearsal cutover (staging)**: freeze → snapshot/hash → import → validation report → flip domain map → smoke the full loop (plant→water→harvest→npc sell→order place/fill→contract→gather→contribute→mill→craft) with two clients → reverse export diff against the source file.
3. **Production cutover** (single window): repeat the ceremony; flip is one gateway config change; Node write paths disabled in the same release; `ownership.md` rows 5–11 marked flipped; keep Node read-only.
4. **Post-flip**: observe outbox age, fill p95, ledger conservation audit job; file the follow-ups (deterministic garden catch-up, escrow-residue refund, contract expiry enforcement) as their own proposals.

Rollback: before flip — abort (nothing changed). After flip — forward-fix only; reverse export under write freeze for downgrade/forensics (D13).
