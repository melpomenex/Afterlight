## Context

The Orpheum's field-note stand is generated by the shared world factory from the `theater` manifest entry's `note: [-6, 7.2]` tuple: a 0.8 × 1.2 × 0.6 m box with a `block()` collision and a `field-note` interaction item. The foosball bay and table were added later at `[-5.8, 7.0]`, so the stand's box and collision now land inside the table's ~1.9 × 1.17 m footprint, and the foosball activity anchor is always nearer than the note item, which makes the note unselectable. See `proposal.md` for motivation.

Constraints that shape the approach:

- The manifest (`shared/placeDefinitions.js`) is the single editable source of place content; the world factory builds notes, stands and collision uniformly for every place.
- Notes are client-side only: the committed server projection carries no note fields, and no save data references notes, so removal needs no migration.
- The `theater-district` capability spec exists only inside the unarchived `add-theater-district` change, not in `openspec/specs/`; an OpenSpec `MODIFIED` delta cannot be merged into a spec that does not exist there.

## Goals / Non-Goals

**Goals:**

- Remove the intersecting stand (mesh, collision, interaction) so the foosball table stands clear and its approaches are walkable.
- Make the removal explicit in the manifest and enforceable in tests.
- Keep every other place's field notes, the theater's objective/landmark/seats/screen, and foosball gameplay untouched.

**Non-Goals:**

- No foosball simulation, controls, netcode or presentation changes.
- No world-factory or interaction-framework changes; other places keep their notes.
- No relocation or rewriting of the retired lore, and no edits to the in-flight `add-theater-district` change.

## Decisions

- **Remove the note at the manifest level** — delete `note`, `noteTitle` and `noteBody` from the `theater` entry rather than special-casing the theater in the factory or builder.
  - Rationale: deleting the tuple flows through the one code path every place shares and removes stand, collision and item together; the manifest then describes the real content with no hidden branch.
  - Alternatives: skipping note construction for `theater` in code (hidden special case, leaves misleading manifest data); relocating the coordinate (rejected by explicit user decision); removing only the stand mesh while keeping the item (invisible interactable — worse).
- **New capability `foosball-table-clearance`** rather than a `theater-district` delta.
  - Rationale: the existing `theater-district` spec is not in `openspec/specs/`, and archive hard-errors on a `MODIFIED` delta for a missing spec. A self-contained new capability is the archive-safe way to state the new behavior.
  - Consequence to record: when `add-theater-district` is eventually archived, its "Theater field note" requirement and the "field-note stand" phrase in "Auditorium is navigable" must be dropped or amended to match this capability.
- **Behavior-level tests, not geometry snapshots**:
  - `tests/place-definitions.test.js`: the theater declares no note (replacing the `noteTitle === 'The Orpheum's house rules'` assertion).
  - `tests/districts.test.js`: the note-completeness rule exempts the theater while still requiring its objective/landmark tuple; every other place keeps its note.
  - `tests/foosball-view.test.js`: at the foosball bay, the foosball activity is the only item and its footprint is the only obstacle whose center falls in the bay; no `field-note` item exists in the built theater.
  - Rationale: these survive future scenery edits while failing if a blocker is re-introduced.

## Risks / Trade-offs

- **[The house-rules lore is removed for players]** → Accepted by explicit user decision; the note was unreadable in practice. The copy remains recoverable from the manifest history.
- **[The unarchived `add-theater-district` spec still requires a theater note]** → Recorded in the proposal and here; a future archive of that change must drop the field-note requirement. This change does not edit the other change's artifacts.
- **[Existing tests assume every legacy place has a note]** → Update the two affected assertions; do not weaken the rule for other places.
- **[Future scenery is added inside the bay]** → The clearance test fails on any non-activity item or foreign obstacle in the bay, prompting a placement fix.
