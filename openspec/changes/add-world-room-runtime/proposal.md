# Add World Room Runtime (P3)

## Why

Transient world state — movement, room membership, presence, emotes, weather — lives in process-local Maps inside the Node server (`server/world.js`): a `clients` map, a `rooms` map, and a dirty-room set flushed every 100 ms. It works at today's scale, but it has no supervision (a crash loses every room), no bounded state growth guarantees (protocol-catalog §2 documents the duplicate-guestId ghost quirk and the absence of any slow-client handling), and no path to the 1,000-session target. The migration umbrella (`port-backend-to-elixir`) assigns this state to supervised OTP room owner processes in phase P3, after the Phoenix gateway transport (P2) exists to carry the traffic.

This change moves the *transient* world into `Afterlight.World`: a Registry + DynamicSupervisor + one RoomServer GenServer per active room, with movement validation, coalesced 10 Hz presence flushes, and emotes. Node remains authoritative for all **durable** domains (theater, catalog, gardens, economy, restoration, accounts), for the chat relay, and for weather — those continue to be proxied exactly as in P2 (weather authority transfers at the P6 group flip, per review, not here). Two clients seeing equivalent movement state, reconnect resnapshotting, and provably bounded room mailboxes are the exit gate.

## What Changes

- **`Afterlight.World` room runtime.** A Registry (unique names) + DynamicSupervisor + one `RoomServer` GenServer per active room; rooms start lazily on first join and stop (after a grace period) when empty. Room processes own only transient state; a crash loses nothing durable.
- **Room identity.** Rooms are identified internally as `{district_id, instance_id}`, with `instance_id` fixed to `"main"` initially, mapping 1:1 to today's rooms (`market`, `theater`, `foundry`, `trestle`, `frost-spire` as `{district, "main"}`; `garden:<playerId>` as `{"garden", playerId}`). The wire room-id strings are preserved **exactly** — clients join with `join_room {roomId}` using today's ids and never see the internal tuple.
- **Router flip.** The gateway domain table flips the world domain to `phoenix`: `join_room` membership, `movement`, `emote`, and `presence_join`/`presence_leave`/`presence_update` are now answered by the room runtime. Join-time snapshots for Node-owned domains (`garden_state`, `theater_state`, `iptv_state`, `node_state`, `machine_update`) still come from Node: `join_room` is still forwarded to Node's shadow session for membership context (Node gates `garden_action`/`node_harvest` on `currentRoom`), while Node's presence frames are suppressed so there is exactly one writer of presence per routing position. Weather is NOT flipped: Node's `weather_update` stays relayed and `welcome.weather` stays Node-built until the P6 group flip.
- **Membership semantics preserved exactly.** Joiner receives the full room roster (`presence_update`), room receives `presence_join` with the joiner's `{id, nickname, x, z, rotY, walking, sitting}` and the joiner excluded, duplicate `join_room` is a presence no-op, `presence_leave` fires on travel and on disconnect — per protocol-catalog §1/§2.
- **Movement validation additions, documented as deliberate tightenings.** Finite checks remain; a server-side world-bounds clamp (`-11.3 < x < 11.3`, `-9.5 < z < 10.3`) is added — harmless to legitimate clients because the client already clamps to the same bounds — and arrival time becomes server-owned internally. Flag handling stays permissive in P3 (`sitting`/`airborne` relayed as today; seat-context validation is noted for a later phase, not silently introduced).
- **Coalesced 10 Hz flush with full-roster semantics.** Dirty rooms flush every 100 ms with FULL roster snapshots `{id, x, z, rotY, walking, sitting, airborne}` per actor — no delta encoding; movement is coalesced keeping only the newest pose per actor per tick; room mailboxes are bounded by selective-receive avoidance and outbound buffers are bounded per transport (slow consumers are disconnected and resnapshot on rejoin rather than queueing unbounded frames).
- **Emotes; weather stays relayed.** `emote` validates the 6-id allow-list (`wave`, `dance`, `cheer`, `heart`, `bow`, `shrug`) with the 500 ms per-session cooldown and relays `emote_broadcast {playerId, nickname, emote}` room-scoped. Weather is explicitly out of scope (review correction): Node keeps writing `weather_update` and building `welcome.weather`; authority transfers to the runtime at the P6 group flip, alongside the gardens/economy change whose garden tick consumes it.
- **Presence is a bespoke roster map, not Phoenix Presence.** The RoomServer's roster is the single source of membership truth. Phoenix Presence is explicitly *not* adopted in P3 — and whenever adopted later it must carry coarse membership only, never 10 Hz positions (per `runtime.md`).
- **Duplicate-connect policy fixed deliberately.** Newest connection wins; the older transport is closed with a socket close reason; presence never leaks ghost members. This is the deliberate fix of Node's overwrite-then-evict quirk (protocol-catalog §2) and is the second documented wire-visible tightening (a stale duplicate tab now sees a clean close instead of silent semi-livestate).
- **Failure behavior.** A crashing RoomServer is restarted by the DynamicSupervisor; room members are forced to rejoin (transport closed for that room with a retryable reason, desiredRoom replay does the rest) and receive fresh snapshots; nothing durable is touched.
- **Chat stays on Node.** The chat relay (`chat_send`, `chat_message`, `chat_dm`, `chat_history`, `chat_presence`, `chat_error`) and the IRC bridge remain proxied to Node in P3 — moving chat here would couple this change to the Node IRC bridge boundary; chat moves in `add-social-chat-relay` (the P7 window, per the ownership matrix). Explicit non-goal for this change (the ownership matrix row for chat is annotated accordingly).
- **Telemetry events named now.** `[:afterlight, :room, :join]`, `[:afterlight, :room, :leave]`, `[:afterlight, :room, :tick]` (duration + room size), `[:afterlight, :movement, :coalesced]` (coalesced/dropped counts), `[:afterlight, :room, :stopped]`; dashboards and alerting remain P10 work.
- **Data model: none.** This change introduces no persistent state whatsoever — rooms, rosters, poses, and emote cooldowns are all process memory (Node's weather phase stays in Node process memory until P6); nothing is written to PostgreSQL or `data/*.json`, and no schema changes occur.

Depends on: `add-phoenix-gateway-transport` (pending — provides the Endpoint, UserSocket, signed guest identity, domain router, and the authenticated Node boundary that this change's router flip and suppression rules build on).

## Capabilities

### New Capabilities

- `world-room-runtime`: supervised, single-writer room ownership for transient world state — lazy room lifecycle with exact wire room-id preservation, exact membership/presence semantics, validated and coalesced movement with bounded mailboxes, emotes with allow-list and cooldown, the deliberate duplicate-connect fix, crash-and-resnapshot recovery, and named telemetry events (weather explicitly stays Node-owned until P6).

### Modified Capabilities

- (none — no capability has been archived yet. `gateway-transport`'s routing requirement anticipated this flip: the P2 disposition table is updated by this change's own spec additions, not by weakening that capability — the router, boundary, and identity requirements continue to apply unchanged.)

## Impact

- **Client**: none — room-id strings, message catalog, snapshot ordering, and the 80 ms movement throttle are unchanged; the two documented tightenings (server-side bounds clamp, clean close of a duplicate transport) are invisible to legitimate clients and a strict improvement for stale duplicates.
- **Gateway** (`server_elixir/`): `Gateway.Router` world entry flips to `phoenix`; `GameChannel` gains world message handling (`join_room`, `movement`, `emote`) delegating to `Afterlight.World`; the Node proxy gains the P3 suppression rules (drop Node-emitted `presence_*` while world = phoenix; keep forwarding `join_room` for Node membership context, relay Node join snapshots, and keep relaying Node `weather_update`/`welcome` unchanged — weather does not flip until P6).
- **World runtime** (new, under `server_elixir/lib/afterlight/world/`): `World.Supervisor` (Registry + DynamicSupervisor), `World.RoomServer` (membership roster, pose state, 100 ms flush tick, emote cooldowns), `World.Movement` (validation + coalescing, pure and fixture-testable), `World.Rooms` (room-id ⇄ `{district_id, instance_id}` mapping), `World.Supervisor`-owned telemetry emissions (`World.Weather` lands with the P6 group flip).
- **Node server**: none — `server/world.js` stays as-is for rollback; its presence frames are simply suppressed by the proxy while the flip is active (weather frames keep flowing).
- **Shared**: none — `shared/protocol.js` and `shared/emotes.js` are the frozen parity reference; the Elixir emote allow-list must match it via fixtures.
- **Persistence**: none — explicitly no data model; all world state is transient process memory (movement/presence never become rows, per the ownership matrix).
- **Docs**: `docs/architecture/elixir/ownership.md` rows #3/#4 move to "delivered P3" and row #22 (weather) is annotated as staying with Node until the P6 group flip; protocol-catalog §2 gains the P3 disposition table, the two deliberate tightenings, and the duplicate-connect fix note; row #16 (chat) annotated that the relay moves with `add-social-chat-relay`, not P3.
- **Tests**: fixture-driven two-client movement equivalence against the Node baseline; reconnect resnapshot; mailbox boundedness assertions; duplicate-connect behavior; regression list re-run (self-echo, handler order, airborne edge, `error` consumers); hot-room 50-player simulation with an honest p99 tick < 50 ms *target* measurement.
