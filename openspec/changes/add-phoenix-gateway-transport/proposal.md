# Add Phoenix Gateway Transport (P2)

## Why

The game's realtime transport is a single raw-WebSocket Node process (`server/index.js`), and identity is whatever the client claims: a client-generated `guest_<9 base36>_<ts>` string trusted verbatim, with no signature and no session token (`docs/architecture/elixir/protocol-catalog.md` §4). All HTTP endpoints are unauthenticated. The migration umbrella (`port-backend-to-elixir`) requires an intermediate phase in which Phoenix hosts the transport for the *existing* client while every durable domain is still written by Node — so that authority can later move domain-by-domain behind a router instead of in one big-bang cutover. Today there is no Phoenix socket, no signed credential, and no server-side mechanism that decides who answers a given message.

This change is migration phase P2 (per `docs/architecture/elixir/ownership.md` §2). The Phoenix gateway carries the existing client's traffic; signed guest identity replaces client-trusted guestIds; and a config-owned domain router proxies every still-Node-owned domain to Node over a private authenticated boundary. The world runtime does **not** move in this phase: movement and presence snapshots are relayed from Node so remote avatars keep working. Two browsers joining, traveling, and reconnecting through the Phoenix transport with equivalent state is the exit gate.

## What Changes

- **Phoenix Endpoint + UserSocket on the `/ws` path.** Phoenix serves the socket path `/ws` so the client's URL derivation (`ws(s)://host:3001/ws` today, via `VITE_WS_URL` or its default in `src/net/client.js`) survives unchanged in *shape*. Port coexistence: in dev, Phoenix serves its own port (4000) and Node keeps 3001; the client points at the gateway through the existing build-time `VITE_WS_URL` mechanism plus an explicit transport switch (`VITE_TRANSPORT=phoenix`, default `node`). Nothing changes for players until a deployment opts in.
- **Signed guest credentials.** A new `POST /api/auth/guest` endpoint on the gateway issues a short-lived signed token (`Phoenix.Token`) bound to a server-side session record for that player. Transitional semantics are exact: the historical `guestId` remains the stable player key and continues to work as *identification* (hello still carries it; self-echo filtering and `garden:<guestId>` room ids depend on its continuity); the signed token is what proves possession of the handshake and is the only *authorization* to connect. GuestId alone no longer authorizes a connection. No durable player storage moves — durable accounts land in P4.
- **Channels adapter `src/net/phoenixClient.js` behind the unchanged `NetworkClient` facade.** `src/net/client.js` remains the public API with a pluggable transport, so the constructor shape `new NetworkClient(wsUrl)` and the behaviors pinned by `tests/presence-race.test.js` survive. The adapter unwraps the Phoenix envelope `{topic, event, payload}` → flat `{type: event, ...payload}`; supports multiple handlers per type invoked in registration order; exposes `onConnect`/`onDisconnect`; silently drops sends when closed; retains the 80 ms movement self-throttle; replays `desiredRoom` (`join_room`) on every reconnect in the same handshake ordering as today (hello sent first, then the replayed join), preserving the server-side snapshot ordering `hello → welcome → garden_state → chat_history → join snapshots` from protocol-catalog §2; and guarantees `welcome` arrives after every reconnect (the net indicator and chat enable depend on it).
- **HTTP side channel preserved at the same origin logic.** The gateway reverse-proxies `/api/theater/*` (playlist + EPG uploads, torrent Range streaming) and `/api/health` to Node, so `NetworkClient.apiBase` — derived from the WS URL host — keeps working with no client change, and theater/catalog (still Node-owned in P2) keep working untouched.
- **Domain router.** A config-owned table maps domain → owner (`node` | `phoenix`), evaluated server-side on every message; clients never choose who serves a domain. In P2 every game domain routes to `node`; the router is the mechanism that later phases (P3 world runtime, P4+ Ash domains) flip entry-by-entry.
- **Explicit terminate-vs-proxy disposition for this phase.** Terminated at the gateway: socket connect + token verification, `ping`/`pong`, and connect rate limiting. Relayed 1:1 to Node over the boundary: everything else — `hello`, `set_nickname` (nicknames stay Node-owned until P4), `join_room` and all room membership/roster/snapshot messages, `movement`, `emote`, chat, and every durable-domain message — so movement, presence snapshots, emotes, theater, market, gardens, restoration, and chat behave exactly as today with remote avatars visible.
- **Reconnect without a second logical world session.** The gateway enforces newest-connection-wins per identity: before a new transport is accepted for a player, the previous upstream session is closed first, so Node never holds two sessions for one guestId (mitigating the known duplicate-guestId overwrite/eviction quirk; the full fix lands with the P3 room runtime).
- **Identity/security hardening.** Token verification at connect, authorization on every channel join, identity always derived from the verified session (client-supplied player ids are never trust), connect rate limits, and tokens never logged.
- **Slow-receiver posture made explicit.** During the proxy phase Node's current send behavior is retained (there are no `bufferedAmount` checks today; protocol-catalog §2 documents the absence). The gateway documents this retained posture, adds transport-level timeouts, and defers full outbound bounding to the P3 room runtime.

Depends on: `add-elixir-phoenix-foundation` (landed — this change builds on its Mix app, supervision tree, Endpoint, Repo/config, and CI; it amends the foundation's minimal-tree/no-game-traffic posture, see Modified Capabilities; neither change moves any durable authority).

## Capabilities

### New Capabilities

- `gateway-transport`: Phoenix hosting the existing client's realtime transport with byte-compatible message semantics — the `/ws` socket and envelope unwrap behind the unchanged `NetworkClient` facade, signed guest credentials with documented transitional guestId semantics, the server-side domain router, the private authenticated boundary proxying unmigrated domains (WebSocket and the `/api/theater/*` HTTP side channel) to Node, reconnect/session-stickiness rules, and the security posture (join authorization, rate limits, token secrecy).

### Modified Capabilities

- `elixir-foundation`: the "minimal supervision tree, owning nothing" requirement is amended from P2 on — the tree additionally starts the gateway's transient session registry and connect rate limiter, and the Endpoint accepts game protocol traffic through the P2 socket surface (`/ws` → UserSocket → GameChannel). Full MODIFIED delta in `specs/elixir-foundation/spec.md`. (No capability has been archived yet, so this delta merges when the foundation spec archives; recording it here and as a delta file keeps the archived spec from contradicting the shipped system.) `migration-governance` requirements are satisfied by this change, not altered; `gateway-transport` is the new capability.

## Impact

- **Client**: `src/net/client.js` becomes a facade with a pluggable transport (built-in default remains today's Node WebSocket behavior, keeping `tests/presence-race.test.js` and all raw-socket tests green unchanged); new `src/net/phoenixClient.js` adapter (Phoenix Channels client, envelope unwrap, token acquisition before connect); `src/main.js` instantiation untouched (`new NetworkClient()`).
- **Gateway (new, under `server_elixir/`)**: `AfterlightWeb.Endpoint` + `Router`, `AfterlightWeb.UserSocket` (token verification on connect), `AfterlightWeb.GameChannel`, `Afterlight.Gateway.Router` (domain→owner table), `Afterlight.Gateway.NodeProxy` (1:1 authenticated upstream WebSocket per client session + flat⇄flat frame relay), `AfterlightWeb.HTTPProxy` plug (reverse-proxy `/api/theater/*`, `/api/health` to Node), `Afterlight.Auth` (guest token issue/verify + transient ETS session registry, no DB rows), connect rate limiter, config entries (`config.exs`/`runtime.exs`: gateway port, Node upstream URL, boundary secret, domain table).
- **Node server**: minimal, additive change in `server/index.js` — an optional boundary check on WebSocket upgrade and `/api/*` (reject requests presenting an *invalid* boundary secret; secret-less connections remain accepted during P2 so direct-client rollback keeps working). No game logic moves.
- **Shared**: none — the wire message set (`shared/protocol.js`) is unchanged; the flat JSON message catalog in protocol-catalog §1 is the compatibility contract.
- **Persistence**: none — no durable state moves or changes format in P2; `data/*.json` and Node writers are untouched. (Data model: none.)
- **Docs**: `docs/architecture/elixir/ownership.md` row for transport/signing annotated as delivered by this change; `protocol-catalog.md` gains a §2 note on the gateway disposition table; README/AGENTS notes for the dev port layout and `VITE_TRANSPORT` switch.
- **Tests**: the existing `node --test` suite stays green untouched (Node path unchanged); new adapter unit tests (envelope unwrap, handler ordering, silent-drop, throttle, replay ordering); scripted two-browser join/travel/reconnect verification; the protocol-catalog §5 regression list (self-echo filtering via guestId continuity, duplicate-handler ordering, airborne flag edge, `error` message consumers); a load *note* task measuring slow-receiver queueing behavior through the proxy (full bounding deferred to P3).
