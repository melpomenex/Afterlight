# Design: theater & catalog domains (Phase P5)

## Context

Current facts (from `docs/architecture/elixir/protocol-catalog.md`, `docs/architecture/elixir/parity-notes.md`, and the code):

- Theater state is `{now, queue}` per theater room, owned by `server/theater.js` around the pure reducer `shared/theaterModel.js applyTheaterAction` (ops: add/addMany/remove/playNow/skip/clear/pause/resume/seek/ended/failed/channel; errors are stable reason strings returned as data, never exceptions). Limits: `QUEUE_MAX` 50, `URL_MAX` 2048, `TITLE_MAX` 120, `RESOLVE_MAX` 100. Item ids: `itm_<base36 nowMs>_<5 base36 rand>`; kinds classify via `classifySource` (youtube/vimeo/file/hls/torrent, WHATWG-URL hazards noted in parity-notes §1.6); torrent items carry `infohash/fileIndex/filePath/fileBytes` through `sanitizeTorrentPick`; `ended`/`failed` are guarded by `action.itemId === state.now.id`; the shared clock is `positionSec + (nowMs - updatedAt)/1000` while playing; seek clamps ≥0 and refuses HLS (`seek_unsupported`).
- Every accepted theater change persists via `Storage.save()` (whole `game-state.json` rewrite) and broadcasts `theater_state {theater:{now,queue}, serverNow}`; theater join sends it targeted. `theater_channel` replaces `now` (URL classifies; torrent needs a valid pick).
- Playlist import: `theater_playlist_resolve {requestId, listId}` (room theater, 1 in flight, 10 s cooldown, mix ids `RD*`/`UL*` declined) → `server/youtubePlaylist.js` fetches the watch page (15 s timeout, `FETCH_MAX_BYTES` 3 MiB, `collectVideos` DFS capped at `RESOLVE_MAX`) → targeted `theater_playlist_resolved {requestId, title, videos}` → client confirms via `addMany` → targeted `theater_import_result {queued, skipped, didNotFit}`.
- Catalog: `server/iptv.js` owns `data/iptv.json` (3.6 MB: 2 lists, 16k channels) and `data/epg.json` (9.2 MB: 12k channels, 1.3k with programmes), atomic tmp+rename writes with rollback. Limits in `shared/iptvModel.js`: 24 lists, 8 MiB text, 20k channels/list, 64 MiB EPG, 50k EPG channels, 250k programmes, 300 lookup keys; errors `not_a_playlist/text_too_large/too_many_lists/no_channels/too_many_channels/list_not_found` (+ `persist_failed` at the manager). Wire: `iptv_state` is metadata-only; channels page via `iptv_list_get → iptv_list`; `epg_lookup {keys ≤300} → epg_schedule {entries:[{key, now, next}]}` via per-channel sorted binary search; EPG import index is first-wins (`shared/xmltv.js`).
- HTTP: `POST /api/theater/playlists` (text `?name=` or JSON `{name,url}` server-fetch) and `POST /api/theater/epg` (raw bytes, gzip `1f 8b` magic → `gunzipSync` with `maxOutputLength`); CORS preflight + any-Origin echo + `Vary: Origin` on `/api/theater/*`; caps enforced from Content-Length AND streamed count.
- Torrent playback streams from the Node sidecar (`GET /api/theater/torrent/:infohash/:fileIndex`, Range 206) — that stays Node through P7; only the bill rows and pick fields belong to this change.
- P4 (dependency) provides the actor session, `CommandReceipt`/`OutboxEvent`, and the gateway composition pattern; room runtime (P3) provides the theater topic (`theater:<instance>`) and coalesced broadcast path.

## Goals / Non-Goals

**Goals**

- One durable writer for theater and catalog: PostgreSQL via Ash; Node writes disabled at the flip.
- Reducer-exact behavior: the Elixir port passes the full `applyTheaterAction` op matrix, `classifySource` table, `normalizeTheaterState`, `parseM3U`, `iptvModel`, and `xmltv` fixtures BEFORE authority moves (governance gate).
- Atomic bill mutations: room row lock + monotonic revision + timeline rows commit in one transaction; stale playback reports cannot advance a newer item, even across restarts.
- Byte-compatible wire: `src/ui/theaterScreen.js` unchanged; snapshot payloads, error strings, and import result reports identical.
- Indexed catalog: EPG now/next on indexed rows (≤300 keys per lookup, p95 in single-digit ms); metadata-only snapshots keep the wire the same size as today.
- Hardened-but-compatible uploads: same caps/CORS/gzip behavior on Phoenix, with explicit SSRF defenses on server-side URL fetch.

**Non-Goals**

- No change to torrent streaming, webtorrent lifecycle, or the picker (Node sidecar until P7); only bill rows/pick fields move now.
- No client changes — no new message types, no payload field additions, no LiveView.
- No multi-room theater features; the schema keys rooms so instances can exist, behavior stays the single `theater` room.
- No EPG catch-up/reminders/recording; no per-programme push; lookups stay pull-based.
- No distributed room ownership — the epoch column is a placeholder; leases/fencing are P9.
- No automatic EPG/playlist refresh from remote URLs.

## Decisions

### D1 — Theater data model and atomic commit protocol

*Decision:* Two tables. `theater_rooms` — `room_key text PRIMARY KEY` (today `'theater'`; format `theater:<instance>` allowed), `revision bigint NOT NULL DEFAULT 1` (monotonic, bumped on every accepted mutation), `epoch integer NOT NULL DEFAULT 1` (placeholder; P9 leases take it over), `now_item_id text NULL`, `updated_at bigint NOT NULL`. `theater_items` — `id text PRIMARY KEY` (server-minted `itm_<base36 nowMs>_<5 base36 rand>`; imported ids preserved verbatim), `room_key text NOT NULL REFERENCES theater_rooms(room_key)`, `slot text NOT NULL CHECK (slot IN ('now','queue'))`, `order_index integer NOT NULL` (queue order; 0 for `now`), `kind text NOT NULL` (youtube/vimeo/file/hls/torrent), `url text NOT NULL CHECK (length(url) <= 2048)`, `video_id text NULL`, `title text NOT NULL` (cleanText ≤120), `position_sec double precision NOT NULL DEFAULT 0` (float — parity-notes pins `positionSec` as float), `playing boolean NOT NULL DEFAULT false`, `updated_at bigint NOT NULL` (epoch ms), `by varchar(40) NOT NULL`, `queued_by varchar(40) NOT NULL`, `generation integer NOT NULL DEFAULT 1` (incremented each time an item becomes `now`), `infohash text NULL`, `file_index integer NULL`, `file_path text NULL`, `file_bytes double precision NULL` (float in JS — kept float for parity). Indexes: `theater_items_room_slot_idx (room_key, slot, order_index)`, `theater_items_room_idx (room_key)`. Command path: `BEGIN; SELECT ... FROM theater_rooms WHERE room_key = ? FOR UPDATE;` → load items → apply the pure reducer port → write item diffs (update `now` row, insert/delete/reindex queue rows, bump `generation` on promotion) → `UPDATE theater_rooms SET revision = revision + 1, now_item_id = ...` → `COMMIT` → outbox row (same transaction) drives the `theater_state` broadcast. Durable commands carry the P4 envelope (`request_id`, receipt, `expected_revision` when applicable). Receipt-key coverage per the governance requirement: `theater_playlist_resolve` (and `torrent_resolve` at P7) carry the client `requestId` and use it as the receipt key; the theater queue/control ops (`theater_queue`, `theater_control`, `theater_channel`, `iptv_list_remove`) have no client correlation id, so they get SERVER-MINTED receipt ids with documented NO-DEDUP interim semantics — transport-level at-least-once delivery, with queue/control effects idempotent-by-value where the reducer makes them so (e.g. `pause` twice is the same state) — stated here explicitly.
*Alternative Considered:* persist the timeline as one jsonb blob on the room row (simplest byte-parity). Rejected: rows give the generation/order indexing the stale-report guard and restart recovery need, and keep `now` referentially pinned; the wire snapshot is still composed as `{now, queue}` so parity is unaffected.

### D2 — Reducer port is 1:1; fixtures gate the flip; generation guards stale reports

*Decision:* `Afterlight.Theater.Reducer` ports `applyTheaterAction` state-in/state-out (no DB in the reducer), with the JS hazard classes from `parity-notes.md` pinned by fixtures: `js_round`/`js_to_number` helpers, UTF-16-unit `cleanText` truncation, WHATWG-faithful `classifySource` (hand-rolled scanner per the URL fixture table), `sanitizeTorrentPick` boundaries (including `Number(null)===0` vs undefined), `newItemId` with injected RNG, and `normalizeTheaterState` repair (absent/null `now`, malformed queue entries dropped, ids regenerated when absent — absent vs null kept distinct). Error reason strings are returned as data and re-used byte-identically on the wire. `ended`/`failed` keep the `itemId === now.id` guard AND add a `generation` guard with SERVER-SIDE INFERENCE (review correction — the client sends no generation): the theater room tracks the last delivered `(revision, generation)` per session and stamps each client report with the generation that session last saw; if the room's current `now.generation` is newer than the stamped generation — including the re-promoted-same-id case — the report is rejected with `item_mismatch`. Under the row lock this is race-free; across restarts the generation persisted in PostgreSQL is what makes "stale" decidable at all (the Node in-memory guard died with the process).
*Alternative Considered:* reimplement per-op SQL mutations without the reducer (validate-then-write per field). Rejected: nine ops × guard conditions is exactly where parity bit-rots; one pure module + one fixture suite is the audit trail.

### D3 — Playlist import: preview/confirm preserved; plain Oban worker

*Decision:* `theater_playlist_resolve` behavior is preserved exactly (room theater, one request in flight per room, 10 s cooldown per room, `RD*`/`UL*` mix ids declined with the existing reason). The fetch+extract moves into an Oban worker with unique-job semantics per room (1 in flight is then enforced by the queue, not just a flag), 15 s total timeout, streamed 3 MiB cap, `collectVideos` DFS order parity, `RESOLVE_MAX` 100, and the existing stable failure reasons (`playlist_unreadable`, `playlist_not_public`, `is_mix`). The result lands as a staged preview record (request_id, title, videos) delivered as `theater_playlist_resolved`; the user's confirm is an `addMany` whose `theater_import_result {queued, skipped, didNotFit}` is computed by the reducer exactly as today. Plain Oban is chosen over AshOban: the job is imperative HTTP work with side-effect-free outcome (no resource changes until confirm), and the single worker needs one queue, one uniqueness key, and retries — AshOban's trigger/notify machinery adds configuration without adding correctness here. Reversal is cheap if P6+ wants it.
*Alternative Considered:* AshOban for uniformity with the Ash layer. Rejected for this job shape; revisited if import grows resource-driven steps (e.g. persisted preview resources with Ash-managed lifecycle).

### D4 — Catalog data model: full rows, metadata-only wire, programmes as rows

*Decision:* Four tables plus a single-row guide header. `playlist_lists` — `id text PRIMARY KEY` (existing iptv id format preserved on import), `name varchar(80) NOT NULL`, `added_by varchar(40) NOT NULL`, `added_at bigint NOT NULL`, `channel_count integer NOT NULL DEFAULT 0` (denormalized, maintained in the import transaction). `playlist_channels` — `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `list_id text NOT NULL REFERENCES playlist_lists(id) ON DELETE CASCADE`, `position integer NOT NULL`, `url text NOT NULL`, `name varchar(200) NOT NULL DEFAULT ''`, `group_name varchar(120) NOT NULL DEFAULT ''`, `logo text NULL`, `tvg_id text NULL`, `UNIQUE (list_id, position)`. `epg_guides` — single active guide as one row with fixed id `'active'` (`name varchar(120)`, `updated_at bigint`); upload replaces it and its children in one transaction. `epg_channels` — `guide_id text NOT NULL`, `xmltv_id text NOT NULL`, `names jsonb NOT NULL DEFAULT '[]'`, `icon text NULL`, `PRIMARY KEY (guide_id, xmltv_id)`. `epg_programmes` — `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `guide_id text NOT NULL`, `channel_key text NOT NULL`, `start_ms bigint NOT NULL`, `stop_ms bigint NOT NULL`, `title text NOT NULL`, `sub_title text NULL`, `description text NULL`, with the covering index `epg_programmes_lookup_idx (guide_id, channel_key, start_ms, stop_ms)`. Programmes are ROWS (not interval arrays or per-channel jsonb): the lookup index gives now/next as one indexed range query per key (`start_ms <= now AND stop_ms > now` for "now"; next-nearest for "next"), preserving the binary-search semantics and the first-wins import rule (dedup by channel+start at import, first occurrence wins — matching `shared/xmltv.js`). Uploads validate caps in EXACT JS units: 24 lists, 8 MiB text (character count against `LIST_TEXT_MAX` as today), 20k channels/list, 64 MiB EPG bytes, 50k EPG channels, 250k programmes; error strings byte-identical (`not_a_playlist`, `text_too_large`, `too_many_lists`, `no_channels`, `too_many_channels`, `list_not_found`, `persist_failed` reserved for the persist step's own failure). Wire stays metadata-first: `iptv_state` carries `{lists:[{id,name,channelCount}], epg:{name,channelCount,programmes}|null}`; full channel pages go out only via `iptv_list_get → iptv_list {listId, channels}` — the same shape and size profile as today (worst single list ≈2–3 MB, fetched once per client per session).
*Alternative Considered:* programmes as per-channel interval arrays in jsonb. Rejected: loses the indexed time predicate and DB-side caps; 250k programmes in one blob recreates the rewrite-the-world problem this change exists to remove.

### D5 — Upload endpoints on Phoenix with identical caps; SSRF defenses on fetch

*Decision:* `POST /api/theater/playlists` (UTF-8 text body + `?name=`, or JSON `{name,url}`) and `POST /api/theater/epg` (raw bytes) move to Phoenix controllers. Behavior parity: caps enforced from Content-Length AND streamed count with abort (8 MiB text, 64 MiB EPG), gzip detected by the `1f 8b` magic and inflated with a hard output cap (64 MiB) so decompression bombs fail cleanly with the guide/library unchanged, CORS preflight (`OPTIONS`) + Origin echo + `Vary: Origin` on `/api/theater/*` only, and the same JSON result/error shapes with identical error strings. The router sends these paths to Phoenix and the Node handlers are removed. For the `{url}` fetch variant (and it alone — import resolution is covered in D3), the controller applies explicit SSRF defenses: scheme restricted to http/https, redirect cap 3 with every hop re-validated, resolved addresses checked against loopback/private/link-local/multicast/reserved ranges at connect time, the connection pinned to the validated DNS answer (re-resolution race closed), total 15 s timeout, and the same streamed size cap. This is strictly additive hardening — the happy path and all error shapes are unchanged.
*Alternative Considered:* leave uploads on Node and proxy. Rejected: catalog persistence moves now; proxying uploads would make Node a writer again (violates single-writer) and keep the only unauthenticated write surface off the gateway where the session/middleware layer lives.

### D6 — Import and reverse-export tooling

*Decision:* `mix afterlight.import_theater_catalog` handles three sources, each snapshot-copied and SHA-256-hashed BEFORE reading, each recorded in `system_imports` keyed by domain so a second run against the same snapshot is a no-op: (1) `game-state.json` theater section — `{now, queue}` repaired through the `normalizeTheaterState`-equivalent port before insert (current live data is `{now: null, queue: []}`, so this path must also be a clean no-op on an idle theater), (2) `iptv.json` — lists and channels upserted with positions preserved; validates 2 lists / 16k channels against the snapshot before declaring success, (3) `epg.json` — guide header, channels, programmes bulk-copied (chunked inserts); validates 12k channels / 1.3k with programmes. Any count mismatch exits non-zero and blocks the flip. A partial file (missing section) is a loud-but-bounded outcome: theater tolerates absence (idle), catalog treats a missing `iptv`/`epg` section as "nothing to import" success only if the corresponding live file was never present. `mix afterlight.export_theater` and `mix afterlight.export_catalog` rebuild legacy-shaped JSON from PostgreSQL for rollback rehearsal; both exist and are documented BEFORE the routing flip and run only under an explicit write freeze.
*Alternative Considered:* one mega-importer reading all files in one run. Rejected: the three sources cut over as one phase but validate independently; separate hashes make partial re-import after a failed validation honest.

## Risks / Trade-offs

- *[Parity rot across nine ops + URL classification]* → the full fixture matrix (op × hostile input, ~40 URL cases, absent/null shapes) is the explicit cutover gate; comparator rules per `parity-notes.md` §2.
- *[Row-lock serialization of a busy theater]* → the theater room is one lock; acceptable at current scale (single shared room, low op rate), and the revision+outbox pattern moves to lease-based ownership in P9 rather than optimizing now.
- *[EPG import weight (9.2 MB, 250k-row potential)]* → chunked bulk inserts with `ON CONFLICT DO NOTHING` first-wins semantics; import is a rare, operator-visible job; count validation catches truncation. Lookups post-import are indexed (p95 target: single-digit ms for a 300-key batch — measured in verification, not asserted).
- *[iptv_list payload size unchanged but now assembled from rows]* → composition is one indexed query per page; worst case (~2–3 MB) identical to today, fetched once per client session; metadata snapshots keep broadcast size in the KB range.
- *[Upload abuse persists (no auth on `/api/theater/*` by design today)]* → caps + SSRF defenses land with the move; adding session-gated uploads is a behavior change explicitly out of scope, noted for P10.
- *[Plain Oban vs AshOban divergence]* → documented in D3; uniqueness/timeout/retry behavior is covered by tests so a later migration to AshOban is mechanical.
- *[Torrent sidecar writes theater items?]* → it does not: the sidecar never writes bill rows; Phoenix records pick fields from the resolved command, and playback status stays transient until P7 grants land.
- *[Partial game-state.json ambiguity grows (theater section gone after this flip; players follow at the P6 group flip)]* → importers key on snapshot hash + section presence, per D6; `system_imports` records what each run saw.

## Migration Plan

1. Land reducer/catalog ports + migrations + Oban worker; parity suites green; Node behavior unchanged (no flip yet).
2. Reverse-export tasks (`export_theater`, `export_catalog`) documented and rehearsed against a staging snapshot BEFORE the flip.
3. Cutover ceremony (governance D4): freeze Node theater/catalog writes → snapshot+hash `game-state.json`, `iptv.json`, `epg.json` → `mix afterlight.import_theater_catalog` → validate counts (idle theater; 2 lists/16k channels; 12k/1.3k EPG) → flip the router (`theater_*`, `iptv_*`, `epg_*` messages and `/api/theater/playlists`+`/api/theater/epg` to Phoenix) → disable Node `theater.js`/`iptv.js` writes → originals read-only.
4. Post-flip: revision+outbox broadcasts; Oban import queue live; restart-recovery and stale-report tests re-run against PostgreSQL.
5. Rollback before flip: do nothing (Node untouched). Rollback after flip: reverse export under write freeze is the documented escape hatch; forward-fix preferred once revisions accumulate. Torrent streaming never rolls back with this change (sidecar untouched).

Dependency order: `add-parity-fixture-baseline` → `add-elixir-phoenix-foundation` → `add-phoenix-gateway-transport` → `add-world-room-runtime` → `add-ash-accounts-domain` → **this change** → `add-ash-gardens-economy-restoration` (P6 consumes the receipt/outbox patterns proven here).
