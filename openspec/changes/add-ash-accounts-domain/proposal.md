# Add Ash Accounts Domain (Phase P4)

## Why

Players and guest sessions are the oldest durable state in Afterlight: 26 player records live inside the synchronously rewritten whole-file blob `data/game-state.json` (`server/storage.js`), and identity is a client-generated `guestId` trusted verbatim from localStorage. Phase P2 introduced signed guest credentials at the Phoenix gateway and P3 moved the world runtime to supervised room processes, but every account mutation still round-trips to Node and to a file format that cannot express constraints (nonnegative coins, unique live nicknames) or idempotency. Accounts are the first durable domain with no remaining dependency: P4 makes session identity server-derived and durable, and lands the command-receipt and outbox infrastructure that every later phase (P5 theater/catalog, P6 gardens/economy) builds on. Scope guard (per adversarial review): P4 authority is identity/session-only — Phoenix owns only the new durability (`guest_sessions` token binding/revocation/expiry plus the `CommandReceipt`/`OutboxEvent` infrastructure, created and tested here); the `players` record — nickname, coins, inventory, xp, everything — remains Node-authored in `game-state.json` until the P6 economy-group flip.

## What Changes

- New Ash domain `Afterlight.Accounts` with resources `Player`, `GuestSession`, `CommandReceipt`, and `OutboxEvent`, persisted via AshPostgres. P4 owns only the new durability: session token binding, revocation, and expiry, plus the receipt/outbox infrastructure (created and tested here — economic commands do not flow through Phoenix until P5/P6). The `Player` resource is a schema plus an idempotent shadow import (a migration source read from a `game-state.json` snapshot), marked read-only until the P6 economy-group flip activates it as writer. Nickname uniqueness is a database constraint (case-insensitive on `lower(nickname)`, active players only) created now but constraining writes only from the P6 activation — no separate nickname-claim resource.
- Player fields mirror the current `game-state.json` shape exactly: `id` (the existing string guest id, kept as primary key), `nickname`, `coins`, `xp`, `level`, `reputation`, `reserved_coins`, `inventory` (jsonb, interim), `materials` (jsonb, interim), `current_room`, `last_seen`.
- Actions: `create_guest_session` (signed token bound to a durable session row), session revocation, and a bounded session-expiry reaper; `set_nickname` (sanitization identical to `shared/identity.js`, gated by parity fixtures), `allocate_nickname` (dedup ladder 2..99 then random 3-digit, preserving `resolveDuplicateNickname` semantics), and `touch_last_seen` are implemented against the schema and fixture-tested but NOT routed in P4 — they mutate Node-authored columns and go live with the P6 activation.
- Policies: the actor is always derived from the signed token's server-verified session; client-supplied ids are never authorization; policies allow self-mutations only.
- Node player writes are NOT disabled: there is no forward-write API (no `adjust_balance`/`adjust_inventory` calls from Node — that design was rejected in review). `server/storage.js` is untouched and the `players` section stays Node-authored and live-written; `hello` and `set_nickname` stay relayed to Node for session/room/chat registration (no shadow-session bootstrap is needed because hello is not flipped) and `welcome` stays Node-built.
- Migration tooling: initial `priv/repo/migrations` for the accounts tables, plus `mix afterlight.import_game_state` — reads `players` from a `game-state.json` snapshot into PostgreSQL as a MIGRATION SOURCE for the read-only shadow: snapshots and hashes the source before reading, imports idempotently (second run is a no-op), validates counts against the snapshot, and normalizes the additive-defaults quirk (players missing `materials`/`reservedCoins`) exactly like `normalizePlayer`.
- GuestId transition: P2's signed tokens are bound to `Player` rows. Historical guest ids claim their record during a documented claim window by presenting the localStorage `guestId` alongside the token handshake; the guestId remains a stable lookup key, not a secret.
- Protocol stays untouched in P4: `hello` is relayed, so `welcome`/`inventory_state` remain Node-built with the same player object field set — nothing changes on the wire; nickname sanitize/dedup parity fixtures (from `add-parity-fixture-baseline`) must pass, and the shadow import must round-trip to the same field set, gating the P6 activation.
- Rollback posture: P4 flips no existing authority, so no player reverse export is required here (the P6 economy-group change owns the players cutover ceremony and its reverse export). P4's new durability is additive: rollback reverts session issuance to the P2 transient session registry with Node untouched; after the P6 activation makes PostgreSQL authoritative for players, forward-fix is preferred.

Depends on: `add-world-room-runtime` (P3 room runtime, gateway routing and signed identity from `add-phoenix-gateway-transport`; P4 binds those tokens to durable session rows — the `hello`/`set_nickname` path stays relayed to Node until the P6 activation).

## Capabilities

### New Capabilities

- `accounts-domain`: durable guest sessions in PostgreSQL with the `Player` schema as a read-only shadow import — server-derived identity from signed tokens (session authority only; player data stays Node-authored until P6), nickname sanitization and deduplication ports with JS parity (routed at the P6 activation), active-player nickname uniqueness plus a bounded session-expiry reaper, self-scoped mutation policies, snapshot-hashed idempotent shadow import of legacy players as a migration source, command receipts and outbox events as shared idempotency infrastructure, and the rollback/claim-window contract for the guestId transition.

### Modified Capabilities

None. The governance requirements in `migration-governance` (single writer, parity before authority, durable command contract, cutover honesty) are satisfied by this change, not altered.

## Impact

- **Elixir (new)**: `server_elixir/lib/afterlight/accounts/` (domain, resources, policies, changes), `lib/afterlight/accounts/reducer_support.ex` (nickname sanitize/dedup port), `priv/repo/migrations/*_accounts.exs` (citext extension, tables, constraints, indexes), `lib/mix/tasks/afterlight.import_game_state.ex` (shadow import), `lib/mix/tasks/afterlight.export_players.ex` (rehearsal tooling for the P6 ceremony), gateway session binding on connect (token → durable `GuestSession`), and the bounded session-expiry reaper.
- **Node (modified)**: none in P4 — `hello`/`set_nickname` stay relayed via the P2 router exactly as today and every player write path (including `server/storage.js`) is untouched; no removal of Node files yet (P11 retires them).
- **Client**: none. `src/net/client.js` storage keys, self-filtering (`net.guestId` string equality), and garden room ids (`garden:<guestId>`) are preserved by keeping the guest id as the stable key.
- **Shared**: nothing changes; `shared/identity.js` is frozen as the parity reference for sanitize/dedup fixtures.
- **Persistence**: `data/game-state.json` remains fully Node-owned and live-written in P4; the shadow import reads a hashed snapshot copy without freezing the live file. PostgreSQL becomes durable truth for sessions, receipts, and outbox (new durability); `players` rows are a read-only shadow migration source until P6.
- **Tests**: existing JS tests stay green untouched (Node behavior does not change in P4); new Elixir Ash unit tests, DB integration tests (nonnegative coins, uniqueness constraint, expiry reaper), shadow-import idempotency/count tests, receipt-dedup tests, and duplicate-connect stickiness tests carried over from P3 semantics.
- **Docs**: `docs/architecture/elixir/ownership.md` rows #1/#2 annotated (session authority P4; player data authority stays with the P6 economy-group change); `protocol-catalog.md` §3 persistence map unchanged in P4 (players remain file-written until P6).
