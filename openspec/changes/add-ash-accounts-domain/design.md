# Design: accounts domain (Phase P4)

## Context

Current facts (from `docs/architecture/elixir/protocol-catalog.md` §3–4 and `data/game-state.json`):

- 26 players are stored in `game-state.json` under `players` keyed by guest id, rewritten whole-file on nearly every mutation by `server/storage.js`. Player shape: `{ id, nickname, coins, xp, level, reputation, reservedCoins, inventory: { seeds, produce, reservedProduce, sprinklers }, currentRoom, lastSeen (epoch ms), materials }`.
- `normalizePlayer` (`server/storage.js:79`) applies additive defaults on every read: missing `materials` → `{}` with non-finite/non-positive counts removed and survivors floored; missing `inventory.sprinklers` → `0` (floored). Importers must reproduce this exactly.
- Nicknames: `sanitizeNickname` (`shared/identity.js`) strips HTML tags, control chars, and non-`[\w\s-]` characters, collapses whitespace, truncates to 20 UTF-16 code units, and falls back to a generated nickname below 3 chars. `resolveDuplicateNickname` tries `base`, then `base2..base99`, then `base<random 3-digit>` against the set of ACTIVE nicknames lowercased. Historical players may share a nickname; only live collisions are deduped.
- Guest id: client-generated `guest_<9 base36>_<base36 ts>` in localStorage `afterlight-gardener-guest-id`, embedded in garden room ids (`garden:<guestId>`) and in client self-echo filtering (`net.guestId` string equality). P2 replaced its authorization role with a short-lived signed token; P2/P3 still resolve identity from the proxied Node session.
- Duplicate connect quirk: a second connection with the same guest id overwrites the session entry; the old socket stays open; the first close evicts the surviving session. P3 preserved this; P4 must not create a second logical session on transport reconnect.
- Ownership matrix rows #1/#2 assign accounts + nicknames to `Afterlight.Accounts`; the review-narrowed P4 scope is session/identity durability plus the receipt/outbox infrastructure — player record authority (nicknames included) moves with the P6 economy-group flip (rows #6–#8 normalize wallets/inventory then).

## Goals / Non-Goals

**Goals**

- One durable writer for sessions (the new durability): PostgreSQL via Ash; the `Player` schema lands now as a read-only shadow so its DB-enforced constraints (nonnegative integers, unique active nicknames) are in place and tested for the P6 activation.
- Server-derived actor identity: token → durable `GuestSession` row → bound player id; policies allow self-mutations only.
- `hello`/`set_nickname` stay relayed to Node, so the wire is untouched: `welcome`/`inventory_state` remain Node-built; the JS-exact nickname sanitize/dedup ports are proven by parity fixtures now and route at the P6 activation.
- Idempotent, validated shadow import of the legacy JSON players as a MIGRATION SOURCE (snapshot+hash, count checks, `normalizePlayer` quirk reproduced).
- Command receipts + outbox events land here as shared infrastructure for P5/P6 durable commands (created and test-exercised in P4).
- Documented claim window binding historical localStorage guest ids to imported rows, and rollback honesty (P4 flips no existing authority; the players reverse export moves to the P6 ceremony).

**Non-Goals**

- No normalization of inventory/materials into `inventory_balances`/`wallets` — that is P6 with the rest of the economy group.
- No full AshAuthentication, passwords, or named accounts.
- No change to client identity storage or garden room id format.
- No movement/presence persistence (stays transient, P3 ownership).
- No rewrite of gardens/economy logic in Node and no forward-write API: their handlers keep mutating `state.players[]` (the forwarding design was removed in review).
- No `hello`/`set_nickname` flip: both stay relayed to Node (no shadow-session bootstrap is needed because hello is not flipped).

## Decisions

### D1 — The string guest id stays the primary key

*Decision:* `players.id` is the existing guest id string (`guest_<9 base36>_<base36 ts>`, shape-validated on new rows; imported historical rows keep their exact value). Rationale: the id is already embedded in client localStorage, in garden room ids (`garden:<guestId>`), in self-echo filtering (string equality against `net.guestId`), and in 26 imported records keyed by it. A UUID surrogate would force a mapping table and a lookup on every gateway hop to preserve those invariants, with no security gain — the guest id is documented (D7) as a stable key, not a credential. New rows are minted server-side with the same shape so room id formatting is unchanged.
*Alternative Considered:* UUID v7 primary key + `legacy_guest_id` column. Rejected: client continuity requires the guest id anyway; two keys double the claim-window logic for zero behavioral benefit.

### D2 — Data model: players, guest_sessions, command_receipts, outbox_events

*Decision:* Four tables in the initial accounts migration (citext extension created first):

- `players` — `id text PRIMARY KEY` (guest id, CHECK `id ~ '^guest_[0-9a-z]{9}_[0-9a-z]+$'` for new rows; imported rows validated at import instead of by constraint so odd historical ids are not silently dropped), `nickname text NOT NULL`, `coins integer NOT NULL DEFAULT 0 CHECK (coins >= 0)`, `xp integer NOT NULL DEFAULT 0 CHECK (xp >= 0)`, `level integer NOT NULL DEFAULT 1 CHECK (level >= 1)`, `reputation integer NOT NULL DEFAULT 0 CHECK (reputation >= 0)`, `reserved_coins integer NOT NULL DEFAULT 0 CHECK (reserved_coins >= 0)`, `inventory jsonb NOT NULL DEFAULT '{"seeds":{},"produce":{},"reservedProduce":{},"sprinklers":0}'`, `materials jsonb NOT NULL DEFAULT '{}'`, `current_room text NOT NULL DEFAULT 'market'`, `last_seen bigint NOT NULL` (epoch milliseconds — keeps the wire value and JS `Date.now()` semantics without conversion; fits int8), `active boolean NOT NULL DEFAULT false` (has a live session; session-derived bookkeeping — the only `players` column Phoenix writes in P4 — maintained transactionally with session create/revoke and by the expiry reaper; it drives the nickname index once that activates at P6). Indexes: `players_active_nickname_unique UNIQUE (lower(nickname)) WHERE active` (static boolean predicate, buildable; citext-equivalent via `lower()` + the ASCII guarantee from D5; created in P4 but constraining writes only from the P6 activation, since P4 rows are a read-only shadow), `players_current_room_idx (current_room)`.
- `guest_sessions` — `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`, `player_id text NOT NULL REFERENCES players(id)`, `token_hash text NOT NULL UNIQUE` (SHA-256 of the signed token; the token itself is never stored), `issued_at bigint NOT NULL`, `expires_at bigint NOT NULL`, `revoked_at bigint NULL`. Indexes: `guest_sessions_player_idx (player_id)`, partial `guest_sessions_live_idx (player_id) WHERE revoked_at IS NULL` — `expires_at` is deliberately NOT in the index predicate (a predicate over `now()` is dynamic time and invalid in Postgres index definitions); liveness checks compare `expires_at` in queries, with the index serving the revocation filter.
- `command_receipts` — `actor text NOT NULL REFERENCES players(id)`, `request_id text NOT NULL`, `payload_hash text NOT NULL` (hex SHA-256 of the canonical payload), `outcome jsonb NOT NULL`, `created_at bigint NOT NULL`, `PRIMARY KEY (actor, request_id)` — the dedup key from `runtime.md`; a reused id with a different `payload_hash` is rejected, an exact retry returns the stored outcome.
- `outbox_events` — `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `aggregate text NOT NULL`, `aggregate_id text NOT NULL`, `revision bigint NOT NULL`, `event_type text NOT NULL`, `payload jsonb NOT NULL`, `created_at bigint NOT NULL`, `published_at bigint NULL`. Index: partial `outbox_events_unpublished_idx (id) WHERE published_at IS NULL`.

Integer coins/xp/level/reputation with nonnegative CHECKs satisfy the governance "money correctness" requirement at the DB layer; epoch-ms `bigint` timestamps preserve wire parity (`lastSeen`, `issued_at` all JS-number-safe).
*Alternative Considered:* timestamptz columns converted at the boundary. Rejected for P4: every conversion is a parity hazard for zero gain while the wire speaks epoch ms; revisit only if a consumer needs SQL-time arithmetic.

### D3 — Inventory and materials stay jsonb through P4; P6 normalizes

*Decision:* `inventory` (seeds/produce/reserved_produce/sprinklers) and `materials` are single validated jsonb columns. Ash changes validate shape (string keys, nonnegative integer values, known section keys) and `normalizePlayer`-equivalent normalization runs on import and read, so the interim data is well-formed. Rationale: the player-shaped inventory is mutated today only by Node-resident garden/economy logic that migrates in P6; normalizing now would pull the `inventory_balances` design, the forwarding API surface, and the conservation tests of P6 into P4 while the economy still executes in Node. The tradeoff — no DB-level per-item nonnegative constraint, no `SELECT FOR UPDATE` on individual balances — is acceptable because P4 has no atomic multi-entity economy transactions (those are exactly what P6 adds, at which point the columns are folded into `wallets`/`inventory_balances` and this jsonb is dropped).
*Alternative Considered:* normalize to `inventory_balances` now. Rejected: duplicates the P6 migration in a phase whose gate is identity, not economy; the interim is explicitly time-boxed and the Ash validation keeps the data migration-clean.

### D4 — P4 authority is sessions + receipt/outbox infrastructure only; `players` stay Node-authored until P6

*Decision:* Phoenix takes durable authority ONLY over new durability: the `guest_sessions` table (token binding, revocation, expiry) and the `command_receipts`/`outbox_events` infrastructure (created and tested here; economic commands do not flow through Phoenix until P5/P6). The `players` record — nickname, coins, inventory, xp, everything — remains Node-authored in `game-state.json` until the P6 economy-group flip. Concretely: there is NO forward-write API (no `adjust_balance`/`adjust_inventory` calls from Node — that design was rejected in review); Node handlers keep mutating `state.players[]` and `server/storage.js` keeps persisting the `players` section unchanged. `hello` and `set_nickname` stay relayed to Node for session/room/chat registration — explicitly stated because it means no shadow-session bootstrap is needed (hello is not flipped) — and `welcome` stays Node-built. The `Player` resource in P4 is a schema plus an idempotent shadow import: the mix task reads `players` from a `game-state.json` snapshot into PostgreSQL as a MIGRATION SOURCE, and the rows are marked read-only shadow until P6 activates the resource as writer. The only column Phoenix writes on `players` in P4 is the session-derived `active` flag. `create_guest_session` may insert a stub row (id, the sanitize-fallback placeholder nickname — `nickname` is NOT NULL — and column defaults) for a guest id the snapshot did not contain so the session FK holds, without authoring any player data. This keeps exactly one writer for the players domain (Node) while the session/receipt/outbox durability this change owns is brand-new — nothing to dual-write.
*Alternative Considered:* (a) Node forwards player mutations to Ash now — rejected in review: it would make Phoenix a second writer of player economic state a full phase before the economy logic can move, and the forwarding API would be written and thrown away in P6; (b) full players flip in P4 — rejected: nickname/economic invariants (uniqueness activation, wallet normalization, conservation) are exactly the P6 group, and flipping players alone would strand `reservedCoins`/inventory mutations in Node handlers.

### D5 — Nickname uniqueness via partial unique index on ACTIVE sessions only

*Decision:* Uniqueness is `UNIQUE (lower(nickname)) WHERE active` on `players` (D2). `active` is flipped true in the same transaction that issues a `GuestSession` and false when the player's last live session is revoked OR is observed expired by the bounded session-expiry reaper — a periodic job that flips `active = false` when the player's last live session is revoked or expired, freeing the nickname slot (expiry does not passively flip anything; only the reaper does), so historical duplicates (already present in the import: e.g. two players named `MistyPepper94` at different times) coexist, and only live sessions compete — matching today's `resolveDuplicateNickname(desired, activeNicknames)` semantics. `allocate_nickname` computes candidates (`base`, `base2..base99`, `base<random 3-digit>`) exactly like the JS ladder and inserts; on a unique violation it retries with the next candidate, so the constraint — not the check-then-insert — is the source of truth. Parity note: `sanitizeNickname` output is restricted to `[\w\s-]` (ASCII), where `lower()`/citext folding is identical to JS `toLowerCase()`, so the index and the fixtures cannot diverge; the citext extension is still installed so P6+ can adopt it wholesale if desired. Activation semantics: the index is created in the P4 migration but constrains nothing there — `players` rows are a read-only shadow until the P6 economy-group flip starts player writes, and the ladder (`allocate_nickname`) executes only from that activation; the reaper, by contrast, is P4-active because session lifecycle is P4 authority.
*Alternative Considered:* unconditional citext unique index on `nickname`. Rejected: changes current behavior (historical duplicates are legal and present in the import data) and would fail the import count validation.

### D6 — CommandReceipt and OutboxEvent land here as shared idempotency infrastructure

*Decision:* The receipt table (D2) is written in the same transaction as every durable mutation that carries `{request_id, payload_hash}` from P5 onward; in P4 itself no client durable command routes through Phoenix (economic commands follow in P5/P6), so the mechanism is created and exercised by integration tests — the receipt contract is proven before its first real consumer arrives, not with production traffic. When `set_nickname` routes (P6 activation), it has no client correlation id and therefore takes a SERVER-MINTED receipt id with documented no-dedup interim semantics (transport-level at-least-once; the mutation is idempotent-by-value) per the governance receipt-coverage requirement. Reused `(actor, request_id)` with a different `payload_hash` → reject with a stable error; exact retry → return the stored `outcome` without re-executing. `outbox_events` rows are inserted in the committing transaction (published by a poller/broadcast bridge with at-least-once delivery; consumers dedupe by event id/revision per `migration-governance`).
*Envelope interim semantics (review fix):* the governance durable-command envelope is {protocol_version, request_id, expected_revision, payload}. P4 owns the infrastructure and therefore defines the interim semantics later phases reference: the gateway INJECTS `protocol_version` (clients never send it — adding a wire field would be an undeclared client-visible change); `expected_revision` is REQUIRED-ABSENT for command classes migrated before the client-visible revision surface exists — no current wire payload carries a revision the client could echo (welcome/inventory_state have none), so a revision-guarded command is impossible until a phase declares the revision source. When a phase needs real revision guarding it MUST declare where the client obtains the revision (server-minted, echoed by the gateway) as a tightening with client-impact analysis; until then every migrated class documents `expected_revision: absent (gateway-validated)` and the receipts table records it as NULL. This keeps the governance SHALL satisfiable without inventing a client capability no client has.
*Alternative Considered:* defer both to P5/P6 when first needed. Rejected: the governance durable-command contract is cross-cutting; landing it with the simplest possible mutation (nickname) makes its first real consumer (theater, P5) a user, not a guinea pig.

### D7 — GuestId claim window: the guest id is a stable key, not a secret

*Decision:* Historical players claim their imported row by presenting, in the P2 handshake, their signed token plus the localStorage guestId; the gateway binds the token to `players.id = guestId` when that row exists and has no live conflicting session. The claim window runs from the P4 flip until import completion plus a documented grace period (default 30 days of `last_seen` recency for claimed rows); afterwards the guestId is accepted only as a routing hint, never as authorization, and an unclaimed row is claimable only through the same handshake (documented manual recovery is out of scope until named accounts exist). This is stated plainly in the spec: possession of a guestId string was never secure proof of ownership in the Node era; P4 does not make it one, it stops making it *authorization*.
*Alternative Considered:* require out-of-band recovery for all claims. Rejected: guest accounts have nothing to recover into; the threat model is unchanged from today and is documented rather than overstated.

### D8 — Import and reverse-export tooling

*Decision:* `mix afterlight.import_game_state` reads `players` from a snapshot copy of `game-state.json` as a MIGRATION SOURCE for the read-only shadow (the live file stays Node-owned and live-written in P4; the importer never freezes it): (1) it refuses to run twice against a changed source by recording the snapshot's SHA-256 in a `system_imports` row keyed by domain, (2) copies the file aside and hashes BEFORE reading it, (3) imports players idempotently (upsert by id; second run is a no-op), (4) validates: imported player count equals snapshot `players` count, total coins/xp sums match the snapshot, zero rows failed normalization, (5) tolerates the additive-defaults quirk by applying `normalizePlayer`-equivalent repair (missing `materials`/`reservedCoins`/inventory sections) before insert, and (6) tolerates a partial file — a missing/empty `players` section reports "nothing to import" and exits 0. Imported rows are marked read-only shadow; the authoritative players import happens at the P6 cutover from a fresh frozen snapshot. `mix afterlight.export_players` writes `players` back to JSON from PostgreSQL; it exists as rehearsal tooling for the P6 reverse-export path, is run only under an explicit write freeze, and is expected to become dead weight once forward-fix is the accepted posture.
*Alternative Considered:* one generic JSON importer. Rejected: domain importers keep count validation and repair rules local and honest.

## Risks / Trade-offs

- *[Shadow drift]* imported `players` rows go stale as Node keeps writing `game-state.json` until P6 → accepted: the shadow is a migration source, not a replica; the P6 change re-imports from a fresh frozen snapshot as its cutover source of truth, so no P4 decision depends on shadow freshness.
- *[Shadow write accidents]* a bug could mutate Node-authored columns of a read-only shadow row → the only permitted Phoenix write on `players` in P4 is the session-derived `active` flag; a guard test asserts no other player column is written.
- *[jsonb inventory lacks DB constraints]* per-item nonnegative enforcement is Ash-level until P6 → a bug could admit a negative count. Mitigation: Ash changes validate on every write; import validation reconciles totals; P6 replaces the mechanism.
- *[latency of nickname ladder under contention]* unique-index retry loop could spin under heavy name collision → bounded by the ladder itself (≤99 deterministic candidates + random fallback) and by how few players rename concurrently.
- *[lower() vs citext divergence]* non-ASCII nicknames would case-fold differently in SQL vs JS → impossible post-sanitize (`\w` in JS is ASCII); a fixture pins this.
- *[Claim-window abuse]* anyone holding a guestId string can bind a token to that row → identical to today's trust model (the id was client-asserted), documented in D7 rather than overstated as fixed.
- *[Partial-file ambiguity]* tooling reading a post-flip `game-state.json` must not mistake "no players" for corruption → D8 makes an absent section a success no-op and the snapshot hash distinguishes versions.
- *[welcome stays whole-Node]* `welcome` continues to merge Node player data with Node weather/prices/contracts/orderBook/theater/iptv exactly as in P2/P3 (hello is relayed) → no cross-server composition exists in P4; the P6 change owns composition and pins it with a full field-set parity test.

## Migration Plan

1. Land Ash resources + migration + fixtures; Node behavior unchanged (no routing flip happens in this change).
2. Reverse-export task implemented and rehearsed against a staging snapshot (rehearsal tooling for the P6 ceremony, which owns the actual players cutover).
3. Activation ceremony: snapshot `game-state.json` (hash recorded) → `mix afterlight.import_game_state` reads the players section into PostgreSQL as a MIGRATION SOURCE (Node writes are NOT frozen; the hashed snapshot copy is the import source) → validate counts (26 players, coin totals) → activate durable session issuance (connect binds tokens to `GuestSession` rows, revocation/expiry reaper live). No routing flip: `hello`/`set_nickname` stay relayed and Node `players` persistence continues.
4. Post-activation: receipt/outbox mechanisms proven by tests (no client durable command routes through Phoenix until P5/P6); claim window open on session binding; `game-state.json` remains fully Node-written until the P6 economy-group flip.
5. Rollback: revert session issuance to the P2 transient session registry (Node untouched throughout — P4 moves no existing authority). The players reverse-export/forward-fix story is owned by the P6 ceremony.
